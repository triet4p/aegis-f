## 1. Scope delivered

- **Notes root (`QuickCaptureScreen`)** is now one focused task: a local composer with one primary action, **Save note**, the humane copy “Saved on this device · Works offline · Instant”, an in-page success/failure message, a guarded **Clear draft**, and one navigation row into **Saved notes**. Saving writes `CaptureMessageEntity` through the existing command and starts no hosted run, no ledger record and no link.
- **Saved notes (`SavedNotesScreen`)** is a focused browse child: the bounded newest-first read of active user quick captures, each row showing its text, device-local saved moment and a plain detail/link summary. Empty, loading, read-error and paged states are covered; the bottom bar is hidden and Back returns to the composer with its draft preserved.
- **Saved-note detail (`NoteDetailScreen`)** reads the stored note when opened and shows the exact text, source, recorded moment, summary, the explicit **Discuss with AI** handoff, the existing **Record a transaction** route, the list of details read from the note, and the guarded **Edit note**/**Delete** actions. Delete names the note and the existing source policy in a red destructive confirmation.
- **Note edit (`NoteEditorScreen`)** is a focused child with one Save. It initializes fields and the revision before the form is shown, keeps typed text on conflict, and reloads the stored note only after an explicit confirmation; leaving with edits asks before discarding.
- **Detail editing (`NoteEventScreen`)** is a focused child for one interpretation. A new detail must name an exact, unique excerpt of the current note; the screen shows the source text, an optional amount with a neutral “add an amount, or explain what is missing” hint rather than a premature error, merchant, stated date/time and interval, and the existing unresolved explanation. A detail whose source changed is shown as out of date and offers a new detail from the current text; a refused save keeps typed values visible and offers an explicit reload.
- **Pending bank notification chooser (`NoteDraftChooserScreen`)** is a focused bounded child. Nothing is auto-selected; Attach/Reject are explicit, refused pairs stay refused, an active link must be unlinked before another, and neither action confirms a draft or changes a ledger figure.
- **AI handoff**: the selected note detail sets a shell-owned `ChatNoteContext` and opens the separate Chat root. Chat renders the note first as a visible attached-note card with **Remove attached note** and “Nothing has been sent.” The note is named in a request only while the card is attached; removing it leaves the next request exactly as typed. No request starts from the handoff or from saving a note.
- **Design/UX decisions after the owner’s visual clarification and Main’s direction:** the root is the focused composer and the saved list is its own child (not a composer + inline list + banner stack copied from the prototype render). The AI handoff lives on the selected note, not as a banner that silently picks the newest note. Bulk clear and per-row delete were not invented; safe delete remains reachable in the focused detail. The separate cards, left-aligned tab title, sky/primary AI accent and short side-by-side actions follow the S10.2 tokens and the plan’s one-screen/one-task rule rather than the illustrative render’s purple/centered-card composition.
- **Localization/design system:** all new copy has EN/VI parity, the note screens use the shared theme, type scale, `₫` money primitive, 48dp targets, insets/IME padding and non-colour status cues (glyph + word). Copy contains no database, token, prototype or debug jargon.

### 1.1 Round-1 correction

The round-1 assessment (and a concurrent self-audit) found a real functional defect: in
`NoteEventScreen`/`NoteEventLinks`, a **PROPOSED** link was treated as an active link, so the
“Choose a pending bank notification” button was hidden and there was no Attach/Reject surface for
the proposal — a suggested match could not be resolved. Candidate 2 blocks the chooser only on an
**ACCEPTED** link; a proposed pair now opens the focused chooser and can be Attached or Rejected.
`S104NotesJournalInstrumentedTest.proposedLinkIsResolvableFromTheFocusedChooser` seeds a synthetic
in-memory pending draft, proposes it, captures the proposed chooser, attaches it, captures the
accepted chooser and event link state, unlinks it, then rejects the pair and captures the refused
state. The same test closes the candidate-1 evidence gap where `NoteDraftChooserScreen` had no
runtime exercise. Also corrected in this pass: the chooser no longer repeats the bank name in its
fact line, no longer shows the contradictory “Needs decision” chip beside a decided link, and uses
plain “limited” wording instead of “bounded”.

## 5. Limitations and rejected measurements

- The system font scale and system theme were not changed; 1.5× is app-scoped instrumentation and light/dark are the in-app choice plus the device’s system dark. The notification-access/service state and network settings were not toggled.
- Offline was not forced by a network toggle (prohibited). Save/browse/edit/details are Room-only and the production check shows no new agent run; this is a code-path and stored-state fact, not a toggled-network observation.
- Save/read failures and concurrent edits use isolated in-memory/file-backed databases, not a corrupted owner database; the real UI recovery was exercised at the Composition boundary.
- Process recreation was proven by real `am force-stop`/relaunch on the installed production app. No `am kill`-style transient-only recreation claim is made.
- The existing `TransactionEditorScreen` at 1.5× wraps “Internal transfer” and “Expense” segments mid-word; that screen is S10.7’s scope and was not redesigned here. The existing Chat provider/config panel retains its S10.2 copy until S10.5.
- The `note_events` identity rows remain after delete by the app’s existing source policy; their derived reading and amount are cleared. This is preserved behavior, not a leak of the deleted text.
- Five `workflow_operations` audit rows from the owned commands remain in production; they contain no note text and are the app’s normal idempotency/audit record.
- The pending-notification chooser’s proposed/accepted/refused states are proven with a synthetic pending draft in the test’s in-memory database, not with a production draft link; no production link was created or changed. The production side proves the note, details, manual route and Chat handoff only.
