## 3. Minimal next diagnosis (established from the trace)

The stream cadence is **one chunk per ~1,006 ms** for all 1,366 chunks. That matches the hold
loop's `delay(1_000)` + `compose.mainClock.advanceTimeBy(1_000)` exactly, while provider and DB
slowdowns would be irregular. The run was therefore throttled by the interactive hold's clock
pumping (one frame-advance per second), not by the provider. That also explains the 353,126-byte
unread socket backlog observed at 18:24: the app was not draining faster than the pumped frames.
A future interactive attempt must advance the Compose test clock continuously at frame rate (or
avoid the Compose test clock for the live run) so the stream is consumed at production speed.
This is a source change outside the paused scope and needs a fresh bounded assignment.

Note: an earlier attempt at a thread-stack diagnostic (`run-as … kill -3 <pid>`) produced
`/data/anr/trace_00` (18:30:06) but that file is not readable from the shell (`Permission denied`),
so it is not used as evidence.
