## 4. Exact blockers with discriminating evidence

1. **Anchor-binding gap for clarification-supplied dates (source-cited, not inferred from one bad
   ref).** `record_event` rejected the snack anchor with `REFERENCE_KIND_MISMATCH`,
   `$.anchor_ref`, constraint `anchor_from_selected_occurrence`, *"Use an anchor built from this
   occurrence's observed date/time references."* (`retryable:true`). Reading the production code
   explains it deterministically:
   - `select_source` issues each value alias with `linkedSubjectKey = "source:<capture>:<start>:<end>"`
     (`AgentToolRuntime.valueRefsIn`). `make_time_anchor` then issues the anchor with
     `linkedSubjectKey = date.bindingKey()` and **no `eventId`**
     (`AgentToolRuntime.makeTimeAnchor`). `record_event` accepts the anchor only if
     `bindingCompatible(source, anchor)` (`AgentToolRuntime.recordEvent`), which compares
     `effectiveKey(source)` with `effectiveKey(anchor)` and falls back to the `eventId` clause.
   - For an *occurrence-sourced* date the anchor's key equals the source key, so the normal path
     works. For a *clarification-sourced* date, `issueClarificationValue` sets
     `linkedSubjectKey = subject.bindingKey()` = `"event:<id>"` (`AgentToolRuntime.registerClarification`),
     so the anchor's key becomes `"event:<id>"` while it carries no `eventId`; the source key is
     `"source:<capture>:<start>:<end>"`. `bindingCompatible` therefore returns false in every
     branch, deterministically, for any clarification-grounded anchor. Compare `anchorsFor`, which
     issues existing-event anchors with both `eventId = event.id` and
     `linkedSubjectKey = sourceRefKey(...)` — the clarification-built anchor is missing exactly
     that binding.
   - So the tool schema's promise that a temporal value may come from "the selected occurrence **or
     its linked clarification**" (and `bindingCompatible`'s explicit CLARIFICATION branches) is not
     reachable through `make_time_anchor` → `record_event`; the missing capability is the anchor's
     clarification/occurrence binding, not the clarification value itself. The clarification answer
     *is* accepted by `make_time_anchor` (the clarification value carries `eventId`, and the
     source value aliases carry the same `eventId`, so `bindingCompatible(date, time)` passes via
     its `eventId` clause) — it is the produced anchor that cannot be bound back to the occurrence.
   - Note-level day scope: legal only while the day token lies **inside** the selected occurrence,
     because occurrence value aliases bind to that source key. A note that states the day once and
     then two purchases cannot use that path for the second event after the first is recorded:
     a span containing both the day and the second purchase overlaps the first event's span, and
     `record_event` refuses an overlapping reading at different boundaries
     (`selected_span_matches_existing_reading`).
   - The model's failing call additionally passed a `date_ref` (`r_049f9a…`) that no tool result had
     issued; the contract rightly refused that argument. It is a separate, model-side error, and it
     does not change the deterministic gap above.
   - The model's own trial-2 clarification states the same block from the product side: the chosen
     draft *"cannot be attached until the event has [a date]"*.
2. **Run-level turn budget across clarification attempts.** `WorkflowRunLimits.maxTurns = 12`
   counts run-wide, not per attempt: trial 2 used 6 turns in attempt 1 and 6 in attempt 2, so the
   answer to the second clarification started attempt 3 at the cap and it failed in 425 ms. The
   workflow needed at least two more tool turns (ground #49, attach link, categorize #16).
   This is a quantitative-gate observation for Main/owner; **the budget was not raised** and no
   schema/validation was changed.
