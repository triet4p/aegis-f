## Executive Summary

Task S9.6 delivers complete actionable Chat outcome presentations, live-state observation, user repair and link decisions directly in Chat, visible-scope follow-up bounding, and restart resilience. The implementation establishes the following core invariants:

1. **Actionable Live Outcome Presentation:** `ChatOutcomeSection` replaces static/prose outcome renderings with live-queried cards for each verified effect (`ChatEventCard`, `ChatLinkCard`, `ChatCategoryCard`, `ChatReplayCard`, and explicit `NoEffect` panels). Every card re-queries its current database state via `WorkflowQueryService` rather than displaying stale claims from earlier execution receipts. If a stored revision has changed since the run executed, the card explicitly warns the user ("Changed since this run: the run reported revision X, the current revision is Y. Actions below use the current revision.").
2. **Direct In-Chat Extraction and Link Repairs:** Users can repair readings and links directly from the Chat screen without navigating transaction-by-transaction:
   - For events: `InterpretationEditorDialog` (editing source span, normalized text, amount, merchant, and time anchor) and `CandidateDraftBrowserDialog` (browsing and linking candidate bank drafts) are directly reachable from `ChatEventCard`.
   - For links: `Attach draft` (transitions `PROPOSED` to `ACCEPTED`), `Reject` (transitions `PROPOSED` to retained `REJECTED`), and `Unlink draft` (transitions `ACCEPTED` back to unlinked `PROPOSED`) buttons operate atomically via `WorkflowCommandService`.
   - For captures: `QuickCaptureHistoryCard` provides in-Chat `Edit saved capture` and `Cancel` capabilities.
3. **Strict Visible-Scope Follow-Up Bounding:** Follow-up queries submitted in Chat resolve strictly against cards visible in the settled outcome (`visibleRefsOf`). If a user prompt names a row outside visible scope (e.g. `attach draft #99`), or uses an ambiguous pronoun/reference with multiple visible cards (`attach that one`, or naming multiple visible IDs), `resolveFollowUpReference` returns `null`. The UI prompts the user ("Which one do you mean? Choose one of the cards above, or name its event, draft, or link number — nothing was changed") and refuses to mutate an arbitrary draft. A consumer test in `BoundedWorkflowExecutorTest` proves that a follow-up prompt referencing a hidden draft outside the visible scope never mutates it, leaves it `PENDING`, creates no link, and writes no ledger rows.
4. **Consumed Continuation and Follow-Up Handle Expiry Hygiene:** In `ChatOutcomeCards.kt` and `QuickCaptureScreen.kt`, consumed or expired continuation/follow-up handles (`IllegalStateException` / `IllegalArgumentException`) immediately clear `agentRunState.followUp` and `agentRunState.continuation` to `null`. This prevents stale handle reuse, dead retry buttons, or deceptive UI state when an external session expires.
5. **Authoritative Process-Restart Resilience:** Authoritative financial and workflow state (captures, events, links, categories) resides durably in Room SQLite. On-device physical proof (`s964_seed1.png`, `s964_r1.png`, `s964_rv2.png`) confirms that a unique synthetic capture created before restart survives force-stop and app relaunch without reseeding, visible upon returning to Chat. Transient in-memory chat state (`ChatAgentRunState`) resets cleanly on restart, preventing ghost runs or stale handles.
6. **Immutability of Ledger and Absence of Autonomous Authority:** All link actions (`Attach`, `Reject`, `Unlink`) and category cards explicitly retain draft status as `PENDING` and write zero ledger rows (`transactionDao().findAll().isEmpty()`). Category selection and link acceptance never confirm a financial transaction or bypass user review.
7. **Clean Scaffolding Removal per Main Direction:** Flaky Compose test-tag instrumentation (`chat-capture-{id}`) and the failing `productionChatReloadsSavedUnresolvedCaptureAfterRestart` test (which failed due to Compose LazyColumn offscreen composition limits rather than a product defect) have been retired per Main instructions. The failure evidence is preserved in `evidence/S9.6-a3/FACTUAL-AUDIT.md` and `evidence/S9.6-a4/CRITERION-MATRIX.md`, and actual surface proof with scripted ADB (`ACTION-TRANSCRIPT.md`) verifies the behavior. A mock wiring test for the AppShell record callback was also removed, leaving only meaningful boundary tests.

Independent verification confirms clean builds, complete JVM suites (567 tests, 0 failures, 3 live-smoke skips), clean Android lint (0 errors), successful isolated APK assemblies, physical phone instrumented execution with 3 test cases (`S96ActionableChatPhoneInstrumentedTest`: Unlink, Attach, Reject, all with PENDING draft and empty ledger assertions), and physical phone production surface proof with 67 PNG/XML records.
