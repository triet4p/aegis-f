## Detailed Evidence Assessment

### 1. Bounded Event Candidate Retrieval & Scope Incompleteness Safety

- **Session grant bound:** `QuickCaptureScreen.kt:258-270` queries `DraftCandidateQuery` with `bounds = QueryPageRequest(limit = 32, offset = 0)` and computes `draftScopeComplete = !pendingDraftPage.hasMore`. The granted draft IDs are passed via `WorkflowCallerScope.AgentSession(..., draftIds = ..., draftScopeComplete = ...)`.
- **Primary-key bounded lookup:** In `PendingBankDraftDao.findPendingByIds(draftIds)`, the DAO queries only drafts whose IDs are in the granted set (`SELECT * FROM pending_bank_drafts WHERE id IN (:draftIds) AND reviewStatus = 'PENDING' AND confirmedTransactionId IS NULL`). Unbounded table scans are architecturally blocked.
- **Transaction recheck:** In `WorkflowQueryService.matchDraftCandidates`, the query verifies that `authorizedDraftIds.size <= QueryPageRequest.MAX_PAGE_SIZE` (32) and executes a bounded recheck inside a Room transaction (`pendingNow = draftCandidates(DraftCandidateQuery(reviewStatus = IntakeReviewStatus.PENDING, bounds = QueryPageRequest(limit = (authorizedDraftIds.size + 1).coerceAtMost(QueryPageRequest.MAX_PAGE_SIZE))))`). If `!pendingNow.hasMore && pendingIdsStillGranted && pendingDatabaseComplete` holds, `pendingDatabaseComplete` is verified true.
- **Incompleteness protection:** If the pending draft pool exceeds 32 drafts or fresh pending rows appeared outside the grant, `pendingDatabaseComplete` evaluates to `false`. In `LinkEvidencePolicy.candidateMatches:206-213`:
  ```kotlin
  val outcome = when {
      !pendingDatabaseComplete -> DraftCandidateMatchOutcome.INCOMPLETE
      matches.size > 1 -> DraftCandidateMatchOutcome.AMBIGUOUS
      matches.isEmpty() && conflicts > 0 -> DraftCandidateMatchOutcome.CONFLICTING
      matches.isEmpty() -> DraftCandidateMatchOutcome.MISSING
      sufficientMatches == 1 -> DraftCandidateMatchOutcome.UNIQUE
      else -> DraftCandidateMatchOutcome.MISSING
  }
  ```
  An incomplete scope forces `outcome = INCOMPLETE`, preventing false `UNIQUE` or `MISSING` claims. In-scope compatible candidates remain visible as partial results. This behavior is comprehensively tested in JVM unit tests: `incomplete pending scope preserves useful candidates without claiming unique or missing` and `fresh pending rows outside an otherwise complete grant prevent a unique claim`.

### 2. Evidence Dimensions & Deterministic Ranking

- **Amount evidence:** `assessDraftCandidate` compares `event.amountVnd` against `effectiveCandidateAmount(draft)`. Exact equality yields `MATCH`; difference yields `CONFLICT`; missing field yields `MISSING`.
- **Time interval evidence:** `assessDraftCandidate` supports single calendar days and start/end intervals with optional wall-clock times. When `hasInterval && intervalUsesClock`, it compares `"$effectiveDate $effectiveTime"` against `"$startDate $anchorTime"` and `"$endDate $intervalEndTime"`. This handles cross-midnight intervals (e.g. `2026-10-21 23:50` to `2026-10-22 00:20`) accurately.
- **Merchant evidence:** `normalizedMerchantPhrase` decomposes Unicode diacritics via NFD normalization, strips accent marks, lowercases, normalizes whitespace and punctuation separators, and verifies whole phrase containment via `" $this ".contains(" $phrase ")`.
- **Deterministic comparator:** Candidate matches sort deterministically by:
  1. Amount match (`MATCH` > others);
  2. Transaction time match (`MATCH` > others);
  3. Merchant match (`MATCH` > others);
  4. Point time distance in minutes ascending (ordering only; does not establish identity);
  5. Draft creation timestamp descending;
  6. Draft ID descending.
- **Fixed rationale:** `rankingRationale` contains fixed explanatory strings generated by application logic, completely independent of model certainty or category assignment.

### 3. Transaction Time vs. Delayed Notification Receipt

- **Receipt time exclusion:** Draft entity stores `postedAtEpochMillis` (intake notification receipt timestamp) separately from `statedDate` and `statedTime` (parsed transaction date and time). `LinkEvidencePolicy` never consults `postedAtEpochMillis` for candidate matching, interval testing, or distance ordering.
- **Field disclosure:** Tool results explicitly return `"receipt_time_used": false`.
- **Empirical proof:** In `S92CandidateRetrievalPhoneInstrumentedTest`, draft #1 has `statedDate = "2026-10-22"`, `statedTime = "00:10"`, and `postedAtEpochMillis` corresponding to `00:45`. The event interval spans `23:50` to `00:20`. The transaction at `00:10` matches within the interval and yields `UNIQUE`, whereas `00:45` falls outside the interval. The test verifies this match survives database close and reopen.

### 4. User Correction Precedence & Terminal Row Exclusion

- **Correction priority:**
  - `effectiveCandidateAmount` prioritizes `draft.reviewAmountText` over intake `draft.amountVnd`.
  - `effectiveCandidateDate` prioritizes `draft.reviewDateText` over intake `draft.statedDate`.
  - `effectiveCandidateTime` prioritizes `draft.reviewTimeText` over intake `draft.statedTime`.
  - `effectiveCandidateDescription` prioritizes `draft.reviewMemo` (when `reviewMemoEdited` is true) over intake `draft.memo`.
- **Terminal row exclusion:** Confirmed drafts (`reviewStatus == CONFIRMED` or `confirmedTransactionId != null`) and dismissed drafts (`reviewStatus == DISMISSED`) are excluded at both the SQL query level in `findPendingByIds` and within `LinkEvidencePolicy.candidateMatches`. Confirmed and dismissed drafts are never returned as candidates and do not count toward conflicts. Verified in `AgentToolRuntimeTest: event draft retrieval ranks parsed evidence honors corrections and excludes terminal rows`.

### 5. Unsupported Dimensions & Absence of Fake Proof

  `"unknown_dimensions": ["account", "transaction_type"]`.
- **No substitute heuristics:** Bank name and draft direction are not substituted for account or transaction type. No candidate is excluded on fabricated account/type grounds.
