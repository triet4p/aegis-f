## Executive Summary

Task S9.3 enforces the reversible link policy between note event interpretations and pending bank drafts. The delivery establishes rigorous safety invariants:
1. Automatic attachment by an agent session requires unique, app-computed pair evidence bound to exact source/event/draft revisions, a draft that remains pending and unconfirmed, and a complete bounded recheck confirming the session grant covers every pending draft. Incomplete search scopes (`INCOMPLETE`) and retrieval ranking/merchant similarity never authorize automatic attachment.
2. Two nearby purchases with the same amount remain strictly ambiguous when evaluated against stored bank drafts; `inspectLinkEvidence` reports `AMBIGUOUS` with multiple competitor rows, and agent auto-attachment is refused with `ATTACH_POLICY`.
3. Ambiguous proposals require explicit user resolution. The user can reject an ambiguous candidate and explicitly choose an alternative candidate.
4. User rejections are durable across process restart and Room database reopen; retrying a rejected pair is refused with `LINK_ALREADY_REJECTED`, preventing duplicate link rows or silent resurrection.
5. Link mutations are revision-tracked: stale unlinks conflict, while an unlink specifying the current revision cleanly removes the accepted association without leaving orphaned state.
6. Link decisions and reversals never rewrite note capture text, event interpretation fields (amount/date/normalized text), bank draft fields, or ledger transactions.
7. Autonomous confirmation authority is absent; draft confirmation remains a dedicated user flow.

## Detailed Evidence Assessment

### 1. Unique Evidence-Supported Auto-Attachment Policy

- **Attachment boundary:** In `WorkflowCommandService.kt:406-411` and `attachPolicyRefusal:1770-1815`, automatic attachment for `WorkflowCallerScope.AgentSession` enforces:
  - Scope draft IDs cannot exceed `QueryPageRequest.MAX_PAGE_SIZE` (32);
  - Bounded candidate search via `queries.matchDraftCandidates` must confirm `candidateSearch.pendingDatabaseComplete == true`;
  - The target draft must remain in `IntakeReviewStatus.PENDING` with `confirmedTransactionId == null`;
  - Current evidence computed by `linkEvidence.evidenceFor(event, draft)` must have `verdict == LinkEvidenceVerdict.UNIQUE`;
  - The proposal's stored evidence must match the current evidence across event/draft revisions, candidate competitor counts, duplicate partner counts, and verdict.
- **Physical phone proof:** In `S93ReversibleLinkPhoneInstrumentedTest.kt:105-150`, a unique cafe purchase (64,000 VND at 16:00) with a single matching pending draft has `inspectLinkEvidence` report `LinkEligibility.ELIGIBLE` (`candidateDraftCount == 1`), and `commands.attachLink` succeeds, transitioning the link to `ACCEPTED` at revision 1.

### 2. Complete Scope Enforcement & Incomplete Search Safety

- **Safety invariant:** When candidate retrieval is bounded or fresh pending drafts exist outside the granted page, `matchDraftCandidates` returns `outcome = INCOMPLETE`. Incomplete scope never authorizes auto-attachment, even if one visible candidate appears compatible.
- **Baseline defect reproduced:** In `baseline-incomplete-auto-attach.txt`, pre-fix execution showed that an `INCOMPLETE` candidate search authorized automatic attachment because the boundary only checked pair evidence without rechecking scope completeness.
- **Post-fix verification:** In `S93ReversibleLinkPhoneInstrumentedTest.kt:195-251`, a scenario with 32 decoy drafts and 1 target draft produces `truncatedPage.hasMore == true` and `outcome == INCOMPLETE`. Agent proposal succeeds, but agent `attachLink` is rejected with `WorkflowDenialReason.ATTACH_POLICY`. The link remains `PROPOSED` at revision 0.

### 3. Equal-Amount Nearby Ambiguity & Suggestion Without Auto-Acceptance

- **Ambiguity evaluation:** In `LinkEvidencePolicy.kt:238-242`, `evidenceFor` counts all stored drafts sharing the same whole-dong amount and stated date via `draftDao.countWithAmountAndDate`. When two drafts share the amount and day, `candidateDraftCount == 2`, `soleCandidate` evaluates to `false`, and `reasons` includes `REASON_COMPETING_CANDIDATE`, yielding `LinkEvidenceVerdict.AMBIGUOUS`.
- **Physical phone proof:** In `S93ReversibleLinkPhoneInstrumentedTest.kt:28-83`, two drafts at 15:00 and 15:15 for 28,000 VND yield retrieval `AMBIGUOUS`. `inspectLinkEvidence` confirms `AMBIGUOUS` with `candidateDraftCount == 2`. Agent auto-attachment is denied `ATTACH_POLICY`, and the proposal safely remains `PROPOSED`.

### 4. Explicit Alternate User Choice & User Attachment Authority

- **User override path:** In `WorkflowCommandService.kt:406-411`, `attachPolicyRefusal` applies only to `WorkflowCallerScope.AgentSession`. A user operating under `WorkflowCallerScope.User` can accept an ambiguous proposal or choose an alternate candidate.
- **Physical phone proof:** In `S93ReversibleLinkPhoneInstrumentedTest.kt:84-98`, the user rejects the first 28,000 VND proposal, proposes the second 28,000 VND draft, and successfully attaches it (`Applied(ACCEPTED, revision=1)`).

### 5. Durable Rejection Memory Across Restart & Retry

- **Refusal immutability:** In `EventContextRepository.kt:387-408`, `rejectLink` sets link state to `REJECTED`. In `proposeLink:321-326` and `acceptLink:366`, an existing `REJECTED` link causes immediate return of `ContextLinkResult.Rejected`. In `unlink:420-422`, attempting to unlink a rejected link is refused, preventing silent erasure of refusal memory.
- **Physical phone proof:** In `S93ReversibleLinkPhoneInstrumentedTest.kt:160-175`, the Room database is completely closed and reopened. The rejection persists in `REJECTED` state. Retrying a proposal for the rejected pair returns `WorkflowDenialReason.LINK_ALREADY_REJECTED`, and no duplicate link rows are created.

### 6. Link Revision, Cardinality, and Undo

- **Optimistic revision locking:** `acceptLink`, `rejectLink`, and `unlink` verify `expectedRevision`. In `S93ReversibleLinkPhoneInstrumentedTest.kt:99-104`, a stale unlink specifying revision 0 against an accepted revision 1 link returns `WorkflowCommandOutcome.Conflict`.
- **Safe undo:** Calling `unlinkLink` with current revision 1 succeeds (`Applied(Unlinked)`). The link row is cleanly removed from Room (`findByPair` returns null).

### 7. Immutability of Source Note, Draft Fields, and Ledger

- **Financial isolation:** `EventContextRepository` modifies only `ContextLinkEntity` and refreshes `NoteEventEntity.status`. It never modifies `NoteEventEntity.normalizedText`, `amountVnd`, `anchorDate`, or `merchant`. It never modifies `PendingBankDraftEntity` amounts, dates, or memos. It never creates or modifies transactions in `LedgerRepository`.
- **Physical phone proof:** In `S93ReversibleLinkPhoneInstrumentedTest.kt:183-194, 251`, assertions verify before and after link operations and undo that:
  - Note capture `bodyText` is unchanged;
  - Event `normalizedText`, `amountVnd`, and `anchorDate` are unchanged;
  - First and second bank draft entities are byte/field identical;
  - Ledger transaction table remains completely empty (`database.transactionDao().findAll().map { it.id }` is empty).

### 8. Absence of Confirm Authority

- Neither `attachLink` nor `proposeLink` contains financial confirmation capability. Bank drafts remain in `IntakeReviewStatus.PENDING` with null `confirmedTransactionId`. Confirmation requires the explicit, separate user review flow.

### 9. Authoritative LinkEvidencePolicy vs Old Tests

- The worker documented that an initial attempt to use ranked retrieval `UNIQUE` as attachment authority caused contract regressions and was correctly abandoned.
- The final implementation uses the authoritative `LinkEvidencePolicy.evidenceFor(event, draft)` check, counting all stored competitor rows in Room, combined with `queries.matchDraftCandidates` pending-scope completeness. Both new instrumented phone tests and existing unit tests pass.

### 10. Test Suite Validation & Root Cause of 14 SQLiteCantOpenDatabaseException Failures

- **Investigation of worker-reported failures:** The worker noted 14 `SQLiteCantOpenDatabaseException: unable to open database file (code 14 SQLITE_CANTOPEN)` failures across 5 test classes (`FinancialCommandServiceTest`, `MigrationChainTest`, `PendingBankDraftDeduplicationTest`, `PendingBankDraftMigrationTest`, `CaptureMessagePersistenceTest`) when running `:app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleDebugAndroidTest --max-workers=1`.
- **Root cause analysis:**
  1. The worker modified only `WorkflowCommandService.kt` (agent attach refusal) and docs/tests. None of the failing tests use `AgentSession` or touch the changed code path; they use `WorkflowCallerScope.User`.
  2. The failure stack traces show the exception was thrown in Robolectric's native SQLite helper during `setUp()` at `setJournalMode(SQLiteConnection.java:422)` before any test business logic executed.
  3. Running the affected test classes in isolation (`FinancialCommandServiceTest`, `MigrationChainTest`, `PendingBankDraftDeduplicationTest`, `PendingBankDraftMigrationTest`, `CaptureMessagePersistenceTest`) passed 100% (28/28, 2/2, 6/6, 3/3, 1/1).
  4. Running the full JVM unit test suite (`:app:testDebugUnitTest`) cleanly passed 100%: **551 tests, 0 failures, 3 skipped**.
  5. Conclusion: The failures were purely environmental Windows SQLite file-handle locking / temporary file collision caused by executing concurrent Gradle tasks in a single invocation. Zero code regressions exist.
