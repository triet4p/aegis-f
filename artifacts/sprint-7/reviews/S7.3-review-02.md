## 5. Acceptance Criteria and Verification Evidence

### 5.1 Failing-Before Reproduction
- Test `marking an older attempt does not overwrite a concurrently retargeted question` in `ClassificationWorkLifecycleTest.kt` sets up an active attempt, simulates a concurrent `retarget` to `newestQuestion`, then calls `markExecuting` with the older question.
- Verified in worker history (`history://S73RetargetSilverFix` line 91): executed against base code, the test failed deterministically with `org.junit.ComparisonFailure at ClassificationWorkLifecycleTest.kt:222` (`job.requestedQuestion` was clobbered by `markExecuting`).

### 5.2 Deterministic Race Fix in Room DAO
- `ClassificationWorkDao.kt` method `markExecuting` updated to accept `requestedQuestionBeforeAttempt: String`:
  ```sql
  UPDATE `classification_work` SET `executedQuestion` = :question,
  `requestedQuestion` = CASE WHEN `requestedQuestion` = :requestedQuestionBeforeAttempt
  THEN :question ELSE `requestedQuestion` END
  WHERE `id` = :id AND `state` = '$CLASSIFICATION_WORK_RUNNING'
  AND `ownerToken` = :token
  ```
- If a concurrent `retarget` occurred between `classify()`'s read and `markExecuting`, `requestedQuestion` differs from `requestedQuestionBeforeAttempt`; the CASE statement preserves the retargeted question.
- If no retarget occurred, `requestedQuestion` is aligned with `:question`, ensuring legacy/stale rows do not enter an infinite requeue loop.
- `BankDraftClassificationQueue.kt:511` passes `job.requestedQuestion` (read at the start of `classify()`) to `work.markExecuting(jobId, token, job.requestedQuestion, question)`.

### 5.3 Queue Requeue and Execution of Latest Question
- In `BankDraftClassificationQueue.kt:564`, `settleOutcome` derives `newerQuestion = job.requestedQuestion != question`.
- Because the concurrent retarget was preserved, `newerQuestion` evaluates to true, transitioning the job via `JobTransition.Requeue(attempts = 0, reason = CONTEXT_CHANGED)`.
- The queue consumer wakes and executes the newer question next, as verified in `ClassificationWorkLifecycleTest`:
  ```kotlin
  val result = awaitWork(draftId) { it.state == CLASSIFICATION_WORK_RESULT }
  assertEquals(newestQuestion, result.executedQuestion)
  assertEquals(listOf("newest memo"), engine.questions)
  assertEquals(1, engine.calls)
  ```

### 5.4 Token and Cancel Invariants Preserved
- All transition statements (`markExecuting`, `settle`, `requeue`) remain strictly conditional on `state = RUNNING AND ownerToken = :token`.
