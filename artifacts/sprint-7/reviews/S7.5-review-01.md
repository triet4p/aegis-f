## 3. Acceptance Criteria and Contract Verification

### 3.1 Bounded Reads, Paging, and Hydration Architecture

- **Bounded Query Execution:**
  - `ReviewQueueDao.findOrderPage` runs a single bounded SQL query parameterized with `LIMIT :limit OFFSET :offset`.
  - In `WorkflowQueryService.reviewQueue(query)`: the query requests `bounds.limit + 1` with `bounds.offset`, adhering strictly to the project's standard pattern for computing `hasMore` without unbounded counts.
  - Page hydration: `findDrafts(draftIds)` uses `SELECT * FROM pending_bank_drafts WHERE id IN (:draftIds)` over only the IDs returned on the current bounded page, avoiding in-memory projection bloat or wide row queries during ordering.
- **Strictly Total Order and Boundary Integrity:**
  - The query orders by:
    1. `CASE WHEN :chronological = 0 THEN q.queueRank END ASC`
    2. `CASE WHEN :chronological = 0 AND q.queueRank = 1 THEN q.queueSubkind END ASC`
    3. `CASE WHEN :chronological = 0 AND q.queueRank = 2 THEN q.queueComparableGroup END ASC`
    4. `CASE WHEN :chronological = 0 AND q.queueRank = 2 THEN q.queueConfidence END ASC`
    5. `q.queueCreatedAt ASC`
    6. `q.draftId ASC`
  - Because `draftId` is the unique primary key, the ordering is strictly total: no records can fluctuate or split ties across pages.
  - Verification: `ReviewQueueTest.bounded paging reaches every draft exactly once in the same order` walks 14 fixture rows in 3-row pages across 5 pages; all 14 rows are read without repetition, omission, or page overlap. On device, 510 pending drafts were paged across Page 1 and Page 2 without loss (`paging-page1.png`, `paging-page2.png`).

### 3.2 Queue Ordering and Precedence Verification

The implementation faithfully matches `docs/sprint-7-confidence-queue-policy.md` §§5–7 and §9:

1. **Rank 0 — Unresolved Linking and Data Conflicts (`NEEDS_DECISION`):**
   - Captures: possible-duplicate family membership (`possibleDuplicateOfDraftId IS NOT NULL` or referenced by another draft), `PROPOSED` links (`context_links.state = 'PROPOSED'`), and bank data needing attention (`amountState = 'UNRESOLVED'`, `momentState = 'UNRESOLVED'`, or `parseStatus = 'UNSUPPORTED_FORMAT'`).
   - High scores never promote: Draft 101 with the sharpest confidence (0.9526) in the fixture is placed first in Rank 0; Draft 102 with 0.99 confidence under a `PROPOSED` link stays in Rank 0.
2. **Rank 1 — Stale, Missing, Unknown, Direct, and User-Resolved (`NOT_COMPARABLE`):**
   - Subkinds 1..5 in exact precedence order:
     - 1a Missing (`queueMissing = 1`, subkind 1)
     - 1b Stale (`queueStaleReason IS NOT NULL`, subkind 2): stored confidence is ignored; Draft 106 with 0.9336 stale confidence orders behind missing Draft 105 and ahead of fresh predictions.
     - 1c Unknown (`decisionSource = 'NO_FIT'`, subkind 3): Draft 107 with 0.8565 sharpness on unknown never promotes to Rank 2.
     - 1d Direct (`REMEMBERED_RULE`, `EXPLICIT_CORRECTION`, `CATEGORY_METADATA`, subkind 4): confidence is null.
     - 1e User-Resolved (`reviewCategoryResolved = 1`, subkind 5): user decision is respected and stands waiting for confirmation/dismissal.
3. **Rank 2 — Fresh Comparable Model Predictions (`SUGGESTION`):**
   - Sorted by canonical group key ascending (`s.modelRevision || ' | ' || s.candidateSetVersion || ' | ' || s.candidateIds`), then `queueConfidence ASC` (least certain first), then `queueCreatedAt ASC, draftId ASC`.
   - Verified fixture order (`ReviewQueueTest`): `101, 102, 103, 104, 105, 106, 107, 108, 113, 109, 114, 110, 111, 112`.

### 3.3 Comparability Grouping and Non-Interleaving

- **Canonical Key Formation:**
  - Evaluated option set, model revision, and candidate set version form the key: `modelRevision | candidateSetVersion | candidateIds`.
  - Predictions from different evaluated sets are distinct comparability groups.
- **No Cross-Group Interleaving:**
  - Draft 112 with 0.9526 confidence evaluated over 11 options sorts as its own section after the 5-option group (`G5`: 0.5638 -> 0.6976 -> 0.8010 -> 0.8010), never interleaved by raw score.
  - Screen presentation: `QueueSectionHeader` evaluates `sameQueueSection(first, second)` comparing `group`, `subkind`, and `comparabilityKey`. The 11-option section renders with heading "Compared only within the same 11 evaluated options; lower confidence comes first" (`inbox-6.png`).

### 3.4 Chronological Override

- `ReviewQueueOrder.CHRONOLOGICAL`:
  - When `:chronological = 1`, rank, subkind, comparability group, and confidence terms in the SQL `ORDER BY` evaluate to NULL, yielding pure arrival order: `q.queueCreatedAt ASC, q.draftId ASC`.
  - Verified on host (`ReviewQueueTest.the chronological override reads every pending draft by arrival`) and physical device (`chronological-suggestion.png`): Draft 112 (0.9526 eleven-option draft) appears early according to its arrival instant rather than at the end of the review order; switching back restores review order at page 0 (`review-order-restored.png`).

### 3.5 Focus Stability, Refresh, and Next-Work Behavior

- **Snapshot State Holder (`ReviewQueueFocus`):**
  - `page` is held as an explicit snapshot in Compose state, not a reactive database Flow.
  - A stored prediction or background delivery cannot reorder the page while the user reads.
  - Re-read occurs only on explicit user actions: `refresh()`, `setOrder()`, `nextPage()`, `previousPage()`, `nextWork()`, and screen entry/navigation return (`LaunchedEffect(focus, draftId) { if (draftId == null) focus.refresh() }`).

### 3.6 Disclosed Policy Gap Decisions

The worker disclosed three design decisions addressing areas where policy text required concrete implementation choices:
1. **User-Resolved vs Stale Precedence in Rank 1:** A draft categorized by the user is placed in subkind 5 (`USER_RESOLVED`), even though S7.4 marked its prediction stale with `USER_CATEGORY_CHOSEN`. This ensures the user's explicit decision is prioritized and satisfies the frozen §9 fixture sequence (`108 -> 113 -> 109`).
2. **Rank 0 Non-UNIQUE Evidence Folded into `PROPOSED` Link State:** Settled links (`ACCEPTED` / `REJECTED`) are not kept in conflict Rank 0 indefinitely; checking `state = 'PROPOSED'` accurately captures all unresolved link decisions without permanently trapping accepted links.
3. **Duplicate Family Membership Tracking:** Later drafts pointing at earlier drafts remain in the needs-decision group even if the earlier partner has been dismissed or confirmed, preserving human review authority over uncertain identity.

All three decisions are sound, preserve system invariants, and directly support the policy specification.
