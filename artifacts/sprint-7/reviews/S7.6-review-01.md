### 3.3 Cancel and Retry Controls, Authority, and Discard Behavior

- `BankDraftClassificationQueue` implements `cancel(draftId)` and `retry(draftId)`:
  - `cancel(draftId)` executes a transaction updating active jobs to `CLASSIFICATION_WORK_CANCELLED` with `ClassificationWorkReason.USER_CANCELLED`, and cancels the coroutine handle tracked in `AtomicReference<RunningAttempt>`.
  - In `runAttempt` / `settleOutcome`, the transaction checks `job.state == CLASSIFICATION_WORK_RUNNING && job.ownerToken == token`. If the job was cancelled or changed while inference was executing, the completion is aborted and no snapshot is recorded.
  - Duplicate intake notifications (`admit(draftId)`) respect `USER_CANCELLED` and refuse to re-arm a user-cancelled question behind the user's back.
  - Explicit user retry (`retry(draftId)`) specifies `respectUserCancel = false`, allowing the user to re-arm the draft.
- Host test `ClassificationWorkLifecycleTest."user cancel discards a running answer and an explicit retry asks again"` proves the end-to-end contract:
  - Engine execution is gated; job enters `RUNNING`.
  - `queue.cancel(draftId)` cancels the job; gate is released.
  - Engine completes, but late answer is discarded: `snapshotOf(draftId) == null`, job remains `CANCELLED / USER_CANCELLED`, and `engine.calls` remains 1.
  - Duplicate intake re-admit does not restart inference.
  - `queue.retry(draftId)` re-arms the job, runs a second engine call, and successfully records the snapshot.
  - Zero transactions are written to the ledger (`database.transactionDao().findAll().isEmpty()`).
