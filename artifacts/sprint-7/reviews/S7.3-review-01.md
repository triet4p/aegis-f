## 3. Acceptance Criteria and Contract Verification

### 3.1 Durable States and Resumable Lifecycle Transitions

- **Schema and Entity:**
  - `ClassificationWorkEntity.kt` defines `classification_work` with columns: `id`, `draftId` (UNIQUE), `state`, `requestedQuestion`, `executedQuestion`, `attemptCount`, `snapshotId`, `statusReason`, `ownerToken`, `createdAtEpochMillis`, `updatedAtEpochMillis`.
  - Indices: unique index on `draftId` enforcing exactly one logical job per draft; index on `(state, updatedAtEpochMillis)`.
  - Five explicit, privacy-safe states: `PENDING`, `RUNNING`, `RESULT`, `CANCELLED`, `FAILED`.
- **Atomic State Transitions:**
  - `ClassificationWorkDao.kt` executes single-statement conditional SQL updates for every transition:
    - `claim`: moves `PENDING` to `RUNNING` and increments `attemptCount` only if state is still `PENDING`.
    - `settle`: moves `RUNNING` to a terminal state (`RESULT`, `CANCELLED`, `FAILED`) only if `ownerToken` matches the attempt token.
    - `requeue`: resets `RUNNING` back to `PENDING` only if `ownerToken` matches.
    - `arm`: updates `requestedQuestion`, resets `attemptCount = 0`, and sets state to `PENDING`.
    - `retarget`: replaces `requestedQuestion` of a running job without interrupting the current execution.
    - `resumeInterrupted`: resets all `RUNNING` jobs back to `PENDING` and clears `ownerToken`.
- **Verified on Host & Physical Device:**
  - Host test `a waiting job and an interrupted running job are resumed by the next process` verified.
  - Physical device (§2, `burst-live` vs `burst-killed` vs `burst-resumed`):
    - When force-stopped mid-inference on draft 7, `burst-killed` SQLite confirmed draft 7 remained truthfully `RUNNING` (`attemptCount = 1`, `executedQuestion = aa1d0164f057...`, `snapshotId = NULL`).
    - On relaunch, `BankDraftClassificationQueue.resumeInterruptedWork()` resumed draft 7 to `PENDING`, dropped the interrupted attempt's claim, and completed draft 7 as `RESULT` (`attemptCount = 2`, `snapshotId = 6`).

### 3.2 Revision-Aware Coalescing

- **Question Digest Boundary:**
  - `classificationQuestionDigest()` derives a SHA-256 canonical digest over:
    `["CLASSIFICATION_QUESTION", description.trim(), categoryRevision, ruleRevision, modelRevision, candidateSetVersion, [reading.eventId, reading.text]...]`
  - The draft's own review revision and amount are deliberately omitted from the digest: an amount correction or draft revision bump that does not change description or context links produces the identical question digest and triggers zero inference.
  - Host test `an accepted edit that does not change the model input asks no second inference` verified: saving amount edit from 50,000 to 60,000 VND resulted in 0 additional engine calls; modifying description triggered exactly 1 call for the new question.
- **Rapid Edits Coalescing:**
  - In `BankDraftClassificationQueue.admitQuestion()`:
    - If a job is already `RUNNING`, `work.retarget` updates `requestedQuestion` in place.
    - If a job is `PENDING`, `work.arm` replaces the queued question in place and resets attempt count.
    - When the current run completes, `settleOutcome` detects `newerQuestion = job.requestedQuestion != question` and requeues with `attempts = 0`, avoiding running intermediate wording.
  - Host test `rapid edits keep the newest question and ask the model once per revision` verified: two edits saved during call 1 resulted in only call 1 ("coffee one") and call 2 ("coffee three"); "coffee two" was never asked.
  - Physical device (§6, `rapid-edits`): Draft 58 edited twice in quick succession (`reviewRevision = 2`). Database confirmed exactly 1 `classification_work` row for draft 58 (`RESULT`, `attemptCount = 1`, `requestedQuestion = executedQuestion = 12d92c3a1c8a...`). Logcat confirmed pre-edit question `09106b7827cd` and final question `12d92c3a1c8a`, with zero calls for intermediate text.

### 3.3 Relevant Accepted-Change Triggers Only

- **Command Boundary Hook:**
  - In `WorkflowCommandService.kt`: `notifyAcceptedChange` runs strictly inside `runCommand` *after* `database.withTransaction` has successfully committed, and only if outcome is `WorkflowCommandOutcome.Applied`.
  - Replayed commands, query reads, UI redraws, and refused commands never call `onAcceptedChange`.
- **Classification Relevance Filter:**
  - In `BankDraftClassificationQueue.kt`:
    - `DraftConfirmed` and `DraftDismissed` directly call `cancelForDraft(draftId, DRAFT_REVIEWED)`.
    - `DraftReviewSaved` calls `admitCurrentQuestion(draftId, rearmSameQuestion = false)`.
    - `affectsClassification()` filters for `CaptureRevised`, `CaptureDeleted`, `EventStored`, `EventRevised`, `LinkDecided`, `LinkUnlinked`, `CategoryAdded`, `CategoryRenamed`, `CategoryArchived`, `CategoryDeleted`, `CategoryRuleRemembered`, `CategoryRuleRemoved`.
    - Screen redraws, query reads, and unrelated changes do not affect classification and trigger zero reconciliation.

### 3.4 Bounded Resource Admission and Session Lifecycle

- **Sequential Execution & Bounded Queue:**
  - `BankDraftClassificationQueue` employs a single coroutine worker draining `work.oldestInState(CLASSIFICATION_WORK_PENDING)` sequentially on `Dispatchers.IO`. Peak overlap is strictly 1 across all scenarios.
  - Bounded queue: `maxQueued = 64`. If `work.countInState(PENDING) >= 64`, `admitQuestion` logs a warning and leaves the draft unclassified, preserving intake without blocking or throwing.
  - Retries are bounded to `MAX_ATTEMPTS = 3` per question digest.
- **Inference Session Lifecycle & Diagnostic Logging:**
  - `LayaInferenceLifecycle.kt` keeps sessions open during work and automatically closes them after 30 seconds of inactivity (`SESSION_IDLE_TIMEOUT_MILLIS = 30_000L`).
  - Observed on device (§4):
    `I LayaInference: inference session opened for work          23:39:25.435`
    `I BankDraftClassification: intake classification draft=10 outcome=APPLIED`
    `I LayaInference: inference session released after idle      23:39:56.421` (31 seconds later).
  - Notification listener only persists drafts and invokes `onDraftStored`; it never instantiates or holds an inference session.
  - **Review of Lifecycle Log Guard:**
    - `logInfo(message: String)` in `LayaInferenceLifecycle.kt` wraps `Log.i(TAG, message)` in a minimal `try { Log.i(TAG, message) } catch (_: RuntimeException) {}`.
    - Analysis: On Android devices, this emits the required observability diagnostics for session open and release. In host JVM unit tests without Android mock logging (`LayaInferenceLifecycleTest`), it avoids crashing the inference worker with unmocked method exceptions. This is a clean, boring, minimal 7-line safeguard that addresses environment differences without suppressing any domain errors or introducing third-party logger abstractions.
