### 3.2 Refusal of Stale Completions and In-Transaction Staleness Materialization

- **Freshness Definition:**
  - `dependencies(description, readings, categories)` computes `contextRevision` strictly over `draft.classificationDescription()` and `activeReadings` (`LayaEventReading(event.id, text)`).
  - An amount/moment edit leaves `contextRevision` untouched; a wording change, note interpretation text change, or link addition/removal updates `contextRevision`.
  - Stale reason checks follow the frozen policy §7 reason order:
    1. `USER_CATEGORY_CHOSEN`
    2. `SOURCE_CHANGED` / `CONTEXT_CHANGED`
    3. `CATEGORY_CHANGED`
    4. `RULE_CHANGED`
    5. `MODEL_CHANGED`
    6. `CANDIDATE_SET_CHANGED`
- **Late Refusal and First-Reason Preservation:**
  - In `recordPrediction()`: when `current != expected`, `markFirstReason()` marks the existing snapshot with the first reason it stopped applying. If `staleReason` was already set (e.g., `USER_CATEGORY_CHOSEN`), `snapshotDao.markStaleForDraft()` retains that first-mover reason via `AND staleReason IS NULL`.

    - `an amount correction leaves a stored prediction fresh while a wording change invalidates it`

### 3.3 Category Archive and Delete Guarantees

- **Guarantees and Checks:**
  - `suggestionResolves(categoryId, categories)` enforces that a suggested category must resolve to exactly one active, unarchived category (`!category.archived`).
  - At store time: `recordPrediction()` checks `suggestionResolves()`. If false, the result is refused with `SnapshotWriteResult.Stale` and marked `CATEGORY_CHANGED`.
  - At read time: `snapshotFor()` calls `staleReason()` which re-evaluates `suggestionResolves()`. If an active category was archived or deleted after the snapshot was stored, the read returns `CATEGORY_CHANGED` and materializes it to the database.
  - In-transaction invalidation: `WorkflowCommandService.archiveCategory()` and `deleteCategory()` call `snapshots.markCategoryCatalogChanged()`, executing `markStaleForCategoryRevision` inside the command transaction.
