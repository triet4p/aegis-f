### Outcome

- **Status:** `ready_for_review`.
- **Observable result:** a supported bank notification that reaches the real listener is parsed and durably stored first, and the draft id is then admitted to a new process-owned, single-worker, bounded classification queue. The queue asks the existing command boundary for one classification of that draft, bound to the context/catalog revision it read, with an idempotency key derived from that revision. So:
  - one supported delivery = one draft + one logical work item; the durable `REQUEST_CLASSIFICATION` row is the record of that item, and the stored prediction is its result;
  - a replayed/re-read delivery resolves to the same draft and, once its request was recorded, replays that record (`NO_CHANGE`) without asking the model again; a failed attempt released its key, so a later re-read may retry it honestly;
  - a missing/busy/cancelled/failing model never delays intake: persistence commits first and the work runs off the persistence path, one inference at a time;
  - an unsupported-format draft is stored but schedules nothing (no description to classify); OTP/security, group-summary, empty and redaction-only payloads never reach storage at all;
  - remembered exact-description rules answer before inference through the same boundary; a draft whose category the user already chose is skipped before the model is asked; a category choice is never overwritten;
  - nothing here selects a category, confirms a draft, or writes a ledger record.
- **Remaining criteria/blocker:** none in S7.2 scope. Deliberately not implemented (separate tasks): durable resumable pending/running transitions and revision-aware coalescing/retry admission (S7.3); stale-completion application rules (S7.4); queue ordering/queries (S7.5); status/controls UI (S7.6); measured quality (S7.7); effort comparison (S7.8).
