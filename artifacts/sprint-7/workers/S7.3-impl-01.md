### Outcome

- **Status:** `ready_for_review`.
- **Observable result:** classification work is now a durable, coalescing job per draft instead of a process-only in-memory queue.
  - **Lifecycle and resumption.** `classification_work` stores one row per draft with `PENDING`, `RUNNING`, `RESULT`, `CANCELLED` and `FAILED`; a claim is conditional and token-owned, and its completion/requeue/cancel is conditional on that token. A process that ends mid-inference leaves a truthful `RUNNING` row; the next process returns it to `PENDING` before claiming anything and also drops the dead attempt's durable claim, so the draft is classified instead of staying unclassified. Device run: `resumed 1 interrupted classification job(s)`, same question re-asked, `RESULT` attempt 2, no `PENDING` operation rows.
  - **Revision-aware coalescing.** A question is identified by `classificationQuestionDigest` over the description, the linked event readings, and the catalog/rule/model/candidate-set revisions. The draft's own review revision and amount are deliberately not part of it, so an amount-only correction asks nothing. A newer question replaces the queued one in the same row (`arm`) or the one a running attempt will run next (`retarget`); a job never multiplies. Host: two accepted description edits while an inference is in flight cost exactly two questions (original + latest), never the middle one. Device: two accepted saves on a queued draft ended in one `RESULT` row whose `requestedQuestion == executedQuestion` is the final wording, with no scheduling line for the intermediate revision.
  - **Relevant triggers only.** The command boundary reports an accepted change after its commit and only for an applied outcome. Confirmed/dismissed drafts cancel their job at once; a saved draft review re-checks exactly that draft; context/link/event/capture/catalog/rule changes reconcile the released jobs by comparing the current question with the recorded one. Redraws, reads, replayed requests, refusals and no-changes never schedule work. A fresh stored prediction for the current question is reused as a `RESULT` without inference (upgrade/reconnect path).
  - **Resource admission.** One worker and one model request at a time; a bounded number of waiting jobs (64); at most 3 attempts per question (reset by a new question) with a short back-off for a question another live attempt holds. Intake commits before admission and only records the job: the listener never opens the model or holds a session. Device: one `RUNNING` + N `PENDING` during a burst; the shared lifecycle logs `inference session opened for work` and `inference session released after idle` 31 s later.
  - **User decisions stand.** A draft the user resolved, confirmed or dismissed is cancelled before the model is asked (`DRAFT_RESOLVED` / `DRAFT_REVIEWED`); a missing/unusable model ends in `FAILED` (`MODEL_OR_INFERENCE_FAILED`) with no guessed prediction. A re-read delivery of a still-pending draft re-arms a recorded miss honestly. No path selects a category, confirms a draft or writes a ledger row.
