### Outcome

- **Status:** `ready_for_review`.
- **Observable result:**
  - **The stored prediction's freshness is exactly the model-input identity.** `contextRevision` is now the digest of the draft's working description plus the readings of the active links; the draft's CAS revision, amount and bank evidence no longer contribute. An amount/date/time correction therefore leaves a fresh prediction fresh, while a wording change, a link decision, an unlink, an event-text edit, or a source-text edit changes it. `recordPrediction` and `snapshotFor` recompute it with the same function.
  - **Staleness is materialized at the change that causes it.** Category add/rename/archive/delete and remembered-rule add/remove mark every prediction whose stored catalog/rule revision differs stale inside the same command transaction; a user category resolution marks the draft's prediction `USER_CATEGORY_CHOSEN`; a changed working description marks it `CONTEXT_CHANGED`. Readers of the raw snapshot rows (S7.5) no longer depend on a later per-draft read to learn the row is stale, and the fixed first-reason order is preserved.
  - **A refused late completion now records why.** When the context/catalog/rule/model moved on, the existing prediction is marked with its first stale reason in the same transaction that refuses the late answer. A prediction that still answers the current input is left alone.
  - **A prediction never names an unusable category.** At storage the suggested id must resolve to exactly one active category (the decision's own name is not stored, so a rename is caught by the catalog revision); at read time the same resolution is re-checked, so legacy/older rows whose id no longer resolves read as `CATEGORY_CHANGED` and cannot be offered.
  - **A reverted question is asked again, not replayed.** The queue's classification request key now includes the attempt's own owner token. Without it, linking then unlinking a reading reverted the question to an earlier one whose key was already recorded; the command replayed `NO_CHANGE` and the stale prediction was never replaced. The interrupted-attempt cleanup now reconstructs the same key from the RUNNING row's token. Device run after the fix: unlink → new `PENDING` operation, new question, fresh prediction with no reading.
  - **User choice and archive/delete guarantees unchanged.** No path assigns a category, confirms a draft, writes a ledger row, or clears a user choice except the existing category-deletion rule; bank fields are untouched.
  - **No schema change.** `classification_snapshots` already persisted probability, confidence, unknown share, evaluated candidate ids/order, candidate-set/model revisions and staleness; this task changes validation/materialization only. No migration or upgrade smoke is required; database version stays 12.
  - **Interpretation-text provenance residual:** the snapshot's dependency now includes the linked reading text, so an interpretation-text edit invalidates the stored prediction and a delayed answer is refused; the device run and host tests cover this. The S6 confirmation-`confirmationBinding` residual itself is outside the snapshot contract and untouched.
