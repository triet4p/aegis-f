### Outcome

- **Status:** `ready_for_review`.
- **Observable result:**
  - **The review queue is a bounded, ordered read of the stored drafts.** `ReviewQueueDao` computes each pending draft's rank, subkind, comparability group and ordering confidence in one SQL statement over `pending_bank_drafts`, `classification_snapshots` and `context_links`, and returns one bounded page of the order; the drafts of that page are then read by id, so a page never carries 500 full rows and a page boundary always falls between two whole drafts. Order: unresolved decision (possible-duplicate family either direction, a `PROPOSED` link, unresolved amount/moment, unsupported format) oldest first; then missing → user-chosen → stale → no-fit → direct, each oldest first; then fresh comparable predictions by ascending stored confidence, per comparability section ordered by `modelRevision | candidateSetVersion | evaluated ids`, with creation instant and unique id as the final tie-breakers. The chronological override is the same rows by creation instant and id.
  - **Every draft is in exactly one visible group and none is dropped.** The surface shows a heading per group/subkind (and per comparability section inside the suggestions), each heading states why it is there and how many of its drafts are on the page, and each card states its own group/reason plus its confidence and evaluated scope where a suggestion applies. A group that continues from the previous page says so. Stored confidence on a stale/unknown/user-resolved/conflicted draft is reported as stored but never orders anything; a sharper prediction sorts later in its own section and stays reachable.
  - **Focus does not jump; refresh, order and next-work are explicit.** `ReviewQueueFocus` keeps the shown page a snapshot: a stored score that changes elsewhere (a stored prediction, a category change, a new arrival) cannot reorder the list until the user taps Refresh, switches the order, comes back from a draft, or uses Next work. A new order starts at page 0, a page that lost its rows steps back to the nearest page that still holds rows, and `Next work` re-reads the queue and opens the oldest draft that still needs a decision, excluding the one already open. Only the order and page survive recreation; the rows are always re-read.
  - **Nothing confirms, dismisses, merges or files anything.** The queue read never writes, and the surface only navigates. No threshold, calibration claim or second confidence field was introduced.
- **Design decisions inside gaps the frozen policy leaves open (disclosed):**
  1. Inside the not-comparable group the check precedence is missing → user-chosen → stale → no-fit → direct, and the subkind numbers are the policy's listed order. So a draft the user already categorised is `USER_RESOLVED` (subkind 5) even though S7.4 also marked its prediction `USER_CATEGORY_CHOSEN` stale; the user's decision is the current fact and the stale prediction is its consequence. Without that precedence the policy's own §9 fixture order (…108, 113, 109…) is unreachable, because a user resolution always materialises `USER_CATEGORY_CHOSEN`.
  2. The rank-0 bullet "link evidence that is not `UNIQUE`" is folded into the `PROPOSED` bullet rather than applied to `ACCEPTED` links: the same section states that an `ACCEPTED` link is context and a `REJECTED` link is settled, so the only unresolved link state is `PROPOSED`, which the queue selects regardless of the stored evidence verdict. Turning an accepted association back into a permanent conflict would contradict the settled-decision rule.
  3. Rank 0's duplicate membership counts a family partner regardless of that partner's review state, so a later draft still pointing at a dismissed/confirmed earlier one remains the user's decision.
  - **Migrated callers / removed obsolete path:** the inbox no longer uses the live newest-first draft page. `WorkflowQueryService.observeDraftCandidates` and `PendingBankDraftDao.observePage` were removed with their shared statement's documentation updated; `draftCandidates` stays for the non-review reads that ask for stored intake rows (the capture-event draft picker and existing tests), which is a different question from review priority.
  - **No schema change.** No new table, column or index; database version stays 12; the new DAO is a read-only query, so no migration or populated-data upgrade smoke applies.
