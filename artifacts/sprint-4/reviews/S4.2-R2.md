## 4. New Actionable Findings

### Finding 3: Windows PowerShell 5.1 `Get-FileHash` Failure in Hybrid Environments
- **Severity:** MEDIUM
- **Claim:** Executing `powershell -ExecutionPolicy Bypass -File tools\laya\Invoke-S42ParityProbe.ps1` in Windows PowerShell 5.1 fails immediately at line 125 with `CommandNotFoundException` on `Get-FileHash`.
- **Evidence:** Running `powershell -ExecutionPolicy Bypass -File tools/laya/Invoke-S42ParityProbe.ps1 -DryRun` on the target workstation yields:
  ```
  The term 'Get-FileHash' is not recognized as the name of a cmdlet, function, script file, or operable program.
  ```
  Inspection reveals that on systems where PowerShell 7 is installed, `C:\program files\powershell\7\Modules` is present on the machine's `$env:PSModulePath` ahead of the system directory. When Windows PowerShell 5.1 searches for `Get-FileHash`, it encounters the PS7 version of `Microsoft.PowerShell.Utility`, whose binary cmdlets cannot load under the .NET Framework 4.8 CLR.
  In contrast, running `pwsh -ExecutionPolicy Bypass -File tools/laya/Invoke-S42ParityProbe.ps1 -DryRun` succeeds cleanly.
  Alternatively, explicitly importing `$PSHOME\Modules\Microsoft.PowerShell.Utility\Microsoft.PowerShell.Utility.psd1` in Windows PowerShell 5.1 succeeds.
- **Why it matters:** If the user copies the documented command `powershell -ExecutionPolicy Bypass -File tools\laya\Invoke-S42ParityProbe.ps1` into a standard Windows PowerShell window, the script aborts before checking the device or transferring files.
- **Confidence:** HIGH (reproduced and verified on workstation).
