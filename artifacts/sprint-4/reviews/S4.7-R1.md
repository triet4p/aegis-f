## 1. Executive Summary

Task S4.7 ("Persist explicit user correction rules", plan line 32) requires offering deliberate remember-rule and remove-rule actions for repeated merchant/description patterns, resolving stored explicit rules before neural inference, allowing removal, and avoiding overwriting unrelated transactions or silently generalizing one correction globally.

Independent code inspection confirms that the technical implementation is robust, correct, and completely aligned with project invariants:
- **Persistence & Migration:** Room schema upgraded to version 6 with table `remembered_category_rules`, foreign-key cascade deletion on `categories.id`, and index on `categoryId`. The deterministic migration `MIGRATION_5_6` and Room schema export `6.json` match exactly.
- **Key Normalization & Exact Isolation:** `RememberedCategoryRuleKey` applies strict case-normalization (`Locale.ROOT`) and whitespace collapsing only; punctuation and other characters are preserved, ensuring zero fuzzy generalization. Blank patterns are rejected.
- **Rule Precedence:** In `ManualCategorySuggestion.kt`, `decideRememberedBeforeInference` queries stored rules first; on an active match, neural inference is never invoked. Misses or stale/archived rules fall back cleanly to inference.
- **Review-Only & Stale Protections:** Matching rules require deliberate acceptance ("Use remembered category") to populate form fields; manual category choice does not overwrite stored rules; late async results on changed description or category snapshots are rejected.
- **Existing Records Intact:** Rule operations use a separate Room table; no transaction DAO write path is touched; no existing ledger records or bank drafts are modified.
- **Host Regressions:** Host unit test suite completed with **185 tests, 0 failures, 0 skipped**, including 11 suggestion machine regressions and 2 file-backed Room persistence regressions.
- **APK Build & Install:** The debug APK (`versionCode 4`, SHA-256 `fe3c416dc4d254d92e805a978ce77e25b7a59dc2fac8ef68aef1fd7fc70afcfc`) was installed in place (`adb -d install -r`) with app data directory and inode preserved.

However, the assigned acceptance criterion explicitly includes:
> "Exercise remember→reopen→repeat hit→remove→no hit on actual app UI with synthetic nonfinancial descriptions."

The real-device UI sequence remains unobserved because the authorized phone was in Dozing state (`mWakefulness=Dozing`), `MainActivity` was resumed but invisible (`visible=false`), and the UI hierarchy dump contained only an empty root frame. Main previously requested the user to wake/unlock the phone and foreground Aegis; that physical prerequisite remains pending.

Because actual on-device UI observation is a material acceptance criterion (not waived or fabricated), this review reports **FAIL** per the binding evidence gate rules. The single actionable item is the pending real-device UI check upon user wake/unlock. Zero code rework is required.
