## 3. Technical Analysis

### 3.1 Public Platform API vs. Older-Platform Fallback

In `app/src/main/java/io/github/triet4p/aegisf/notification/NotificationAccess.kt:33-40`:

```kotlin
fun isNotificationAccessGranted(context: Context): Boolean {
    val component = ComponentName(context, BankNotificationListener::class.java)
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O_MR1) {
        val manager = context.getSystemService(NotificationManager::class.java)
        return manager?.isNotificationListenerAccessGranted(component) == true
    }
    return isAccessGrantedLegacy(context, component)
}
```

- **Evaluation:** `NotificationManager.isNotificationListenerAccessGranted(ComponentName)` was introduced in API 27 (Android 8.1 Oreo MR1). Calling it on API versions below 27 would trigger a runtime `NoSuchMethodError`.
- Because Aegis F supports `minSdk = 24`, maintaining `isAccessGrantedLegacy(context, component)`—which queries `Settings.Secure.getString(contentResolver, "enabled_notification_listeners")` and verifies the component flattened string—is the technically sound and necessary fallback for API levels 24, 25, and 26.
- The version guard `Build.VERSION.SDK_INT >= Build.VERSION_CODES.O_MR1` properly partitions official platform queries from the legacy string parse.

### 3.2 AOSP Threading Architecture vs. Claimed "No Main-Thread Blocking"

In `app/src/main/java/io/github/triet4p/aegisf/notification/BankNotificationListener.kt:28-37`:

```kotlin
override fun onListenerConnected() {
    // The allowlist is small in-memory SharedPreferences state, already cached by
    // the framework after first read, so this refreshes synchronously on the
    // callback: any notification delivered at bind time is evaluated against the
    // stored allowlist, never against a transient empty snapshot. The settings
    // screen pushes later saves straight into [allowedPackages], and this read runs
    // on the system callback thread — never the Android main thread.
    allowedPackages = NotificationAccessStore(applicationContext).loadAllowedPackages()
    connectionState.value = ListenerConnection.Connected(System.currentTimeMillis())
}
```

And in worker handoff `artifacts/sprint-3/handoffs/S3.1-A2.md:12`:
> *"The read is small cached SharedPreferences state on the system callback thread, never the Android main thread; no callback can observe the transient empty snapshot..."*

- **AOSP Threading Reality:**
  According to `frameworks/base/core/java/android/service/notification/NotificationListenerService.java` in AOSP:
  1. `NotificationListenerService` attaches an internal handler `mHandler = new MyHandler(getMainLooper())`.
  2. IPC calls from Android `system_server` via the Binder stub `NotificationListenerWrapper` post `MSG_ON_LISTENER_CONNECTED`, `MSG_ON_NOTIFICATION_POSTED`, and `MSG_ON_NOTIFICATION_REMOVED` directly to `mHandler`.
  3. Therefore, since Android 7.0 (API 24, Aegis F's `minSdk`), **all listener callbacks run on the application process's main thread (`Looper.getMainLooper()`)**. There is no separate "system callback thread" inside the app process.
- **Main-Thread I/O Reality:**
  `NotificationAccessStore.loadAllowedPackages()` accesses `getSharedPreferences("bank_notification_settings", Context.MODE_PRIVATE)`. If the listener service is bound by `system_server` on cold process start (e.g., following boot or system rebind without preceding UI activity), `SharedPreferencesImpl.awaitLoadedLocked()` blocks the calling thread until the XML file is loaded from disk.
- **Contract Impact:**
  Sprint 3 acceptance criteria and plan specify: *"ensure callback work does not block the Android main thread"* (`docs/sprint-plans/sprint-3.md:28`). While the risk of an ANR on a tiny preferences file is low, the worker's premise that the callback does not run on the main thread is factually incorrect and introduces synchronous disk I/O on `Looper.getMainLooper()`.

### Finding 2: Synchronous SharedPreferences Read on Android Main Thread (`Looper.getMainLooper()`)

- **Severity:** MEDIUM
- **Target:** `app/src/main/java/io/github/triet4p/aegisf/notification/BankNotificationListener.kt:28-37` and worker artifact/handoff claims.
- **Claim:** The worker asserts that `NotificationAccessStore.loadAllowedPackages()` in `onListenerConnected()` runs on a "system callback thread — never the Android main thread" and causes "no main-thread blocking". In reality, AOSP `NotificationListenerService` callbacks run directly on `Looper.getMainLooper()`, causing synchronous disk I/O on the main thread during cold start.
- **Evidence:**
  - In AOSP `android.service.notification.NotificationListenerService.java`, callbacks are handled by `mHandler = new MyHandler(getMainLooper())`.
  - In `NotificationAccessStore.kt:58-65`, `loadAllowedPackages()` calls `preferences.getStringSet(...)`, which blocks via `awaitLoadedLocked()` if the XML file is still loading from disk.
  - Sprint 3 contract (`docs/sprint-plans/sprint-3.md:28`) specifies: *"ensure callback work does not block the Android main thread"*.
- **Why It Matters:** The implementation introduces main-thread disk I/O under the mistaken premise that listener callbacks run on a background thread. While latency is low for a small preferences file, cold-start binding can cause frame drops or `StrictMode.DiskReadViolation`. The comment and threading model should accurately reflect main-thread execution or offload disk reads appropriately.
- **Confidence:** HIGH

## 7. External Prerequisites & Exact User-Run Next Steps

Because subagents cannot access a physical device or invoke `adb`, the following external verification steps MUST be performed by the user using the debug APK built at `app/build/outputs/apk/debug/app-debug.apk`:

### Step 1: Install Debug APK
Run via PowerShell/Terminal:
```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

### Step 2: Verify Initial Settings State & Restricted Settings
1. Launch **Aegis F** on the phone.
2. Tap **Bank notifications** on the home screen.
3. Observe initial status:
   - `Notification access: Not granted`
   - `Listener: Listener not connected`
   - `Bank apps listed: 0 packages`
4. Tap **Open notification settings**.
   - If the toggle switch for Aegis F is disabled/greyed out ("Restricted setting" on Android 13/14+):
     - Tap **Back** into Aegis F, then tap **Open app info**.
     - In the system App Info page, tap the top-right 3-dot menu (`⋮`).
     - Tap **Allow restricted settings** and confirm with device PIN/fingerprint.
     - Return to Aegis F and tap **Open notification settings** again.
5. Turn ON the switch for **Aegis F** and tap **Allow** on the system confirmation dialog.
6. Return to Aegis F and observe the screen status update on resume:
   - `Notification access: Granted`
   - `Listener: Listener connected` (system server has bound the service).

### Step 3: Verify Bank App Allowlist & Intake Ready Status
1. Tap **Add a bank app**.
2. Type an invalid name (e.g. `VietinBank` or `bank`) and tap **Add**. Confirm it is refused with an error message and nothing is added.
3. Type the real application ID: `com.vietinbank.ipay` and tap **Add**.
4. Confirm `com.vietinbank.ipay` appears in the list with status **Ready**.

### Step 4: Verify Revocation State Update
1. Open the phone's system **Settings** → **Apps** → **Special app access** → **Device & app notifications** (or tap **Review notification access** inside Aegis F).
2. Turn OFF notification access for Aegis F.
3. Return to Aegis F and observe the status update on resume:
   - `Notification access: Not granted`
   - `com.vietinbank.ipay` status changes to **Waiting for access**.

### Step 5: Verify Manual Recording Independence
1. From the home screen, tap **Record a transaction**.
2. Record an expense (e.g. 50,000 VND under Food).
3. Confirm the transaction is saved, visible in **Saved transactions**, and correctly tallied in the **THIS MONTH** card.
4. Verify that manual recording operates without error regardless of whether notification access is granted or revoked.
