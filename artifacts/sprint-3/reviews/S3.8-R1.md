## 1. Executive Summary

This is the mandatory Light-route sprint-wide privacy and intake evidence review gate for task **S3.8** ("Verify real bank intake and document limitations") and attempt **S3.8-A1**. This review evaluates the end-to-end differential privacy, storage boundedness, parser uncertainty, lifecycle recovery, deduplication, atomic confirmation, and terminal identity across the Sprint 3 pipeline (`BankNotificationListener`, `NotificationIntake`, `BankNotificationParser`, `IntakeRepository`, `PendingBankDraftDao`, `BankDraftReviewDao`, `BankDraftReviewRepository`, `LedgerDatabase`).

The review confirms that strong privacy and storage boundaries are implemented throughout the production codebase:
1. **Allowlist-first short-circuit:** Package metadata is checked before accessing notification extras; non-allowlisted packages produce 0 content reads.
2. **Strict filtering:** OTPs, passwords, verification codes, group summaries, empty content, and redaction-only payloads are rejected immediately; no notification bodies, account identifiers, balances, or OTPs are persisted or logged in any app table or log stream.
3. **Conservative parser:** Stated amount and direction (`GD:`) are decoupled from balances (`SDC:`) and account numbers (`TK:`); timestamps preserve wall-clock values without timezone fabrication; direction is explicitly decoupled from ledger type.
4. **Idempotent replay and atomic confirmation:** Repeated deliveries under the same post and evidence digest write nothing; review confirmation commits the draft terminal state, inserts the ledger record, and links the transaction within a single Room database transaction. Deleting the confirmed transaction leaves the draft in terminal `CONFIRMED` state (`onDelete = SET_NULL`), preventing replay recreation.
5. **Reconnection boundaries:** Reconnection reconciles only currently active notifications without claiming access to dismissed or historical notifications.

However, the review identifies one **material unverified acceptance criterion** that blocks a passing verdict:
- The sprint plan Required Verification explicitly requires: *"Test OTP/unrelated/group-summary rejection and two separate equal-amount transactions with distinct references."*
- Worker S3.8-A1 declared this check *"not reachable with the supported format"* because the user-supplied VietinBank sample lacked a standalone reference line, and substituted a test of two byte-identical payloads (`-50,000 VND` with masked `ND: ........`).
- In that substituted test, the second delivery was flagged as a duplicate (`possibleDuplicateOfDraftId = firstId`). In contrast, the assigned requirement was designed to verify that equal-amount transactions carrying distinct reference or memo content (e.g., `ND: REF#1` vs `ND: REF#2`) do **not** collapse and are **not** falsely flagged as duplicates (`possibleDuplicateOfDraftId = null`).
- The underlying architecture already includes `memo` in `draftEvidenceDigest`, so synthetic notifications with distinct reference labels in `ND:` can easily prove this non-collapse behavior on host. Waiving this check unilaterally without verification is an invalid reduction of scope.

Because a material acceptance criterion remains unverified by sound evidence, the verdict is **FAIL** (`advance: false`).

## 2. Actionable Findings and Recommendations

### Finding 1: Unverified Material Criterion — Equal-Amount Transactions with Distinct References (MEDIUM / Actionable Gap)
- **Claim:** The required verification for two separate equal-amount transactions with distinct references was omitted and deemed "unreachable" without justification.
- **Evidence:** 
  - `docs/sprint-plans/sprint-3.md:36`: *"Test OTP/unrelated/group-summary rejection and two separate equal-amount transactions with distinct references."*
  - `artifacts/sprint-3/handoffs/S3.8-A1.md:27`: *"Two separate equal-amount transactions with distinct references (plan wording) | not reachable with the supported format | no supported format states a transaction reference, and the bank context forbids deriving one from TK:/SDC:/ND:."*
  - `artifacts/sprint-3/workers/S3.8-A1.md:276`: *"the plan's 'two separate equal-amount transactions with distinct references' is unreachable with the supported format... distinctness was instead proven by two kept drafts [flagged as possible duplicates]"*.
  - `app/src/test/java/io/github/triet4p/aegisf/data/PendingBankDraftDeduplicationTest.kt` contains 17 tests, but every single test uses `ND: ........` (masked) or different amounts (`-50,000` vs `-60,000`). Not one test exercises equal amounts with distinct memo/reference text.
- **Why It Matters:** The core contract of conservative deduplication is to distinguish between exact replays, uncertain duplicates of identical statements, and distinct real transactions of identical value. When transactions share the same amount and timestamp but carry distinct references/memos, they must not collapse, and crucially, they must not be falsely flagged as duplicates of each other (`possibleDuplicateOfDraftId` must be null). Because `memo` is hashed into `draftEvidenceDigest` (`PendingDraftIdentity.kt:83-118`), the architecture already supports this. Omitting the test leaves a major deduplication guarantee unverified against regression.
- **Confidence:** HIGH.
- **Actionable Target (Source/Host change needed now):**
  1. Add a test in `PendingBankDraftDeduplicationTest.kt` (or permanent verification suite) testing two equal-amount deliveries (e.g., `-50,000 VND`) at the same post time, but with distinct reference labels in `ND:` (e.g., `ND: REF#101` vs `ND: REF#102`).
  2. Verify that:
     - Both drafts are persisted as separate rows.
     - Neither is collapsed or overwritten.
     - Neither draft is flagged as a duplicate of the other (`possibleDuplicateOfDraftId = null`).
     - Both drafts remain independently reviewable and confirmable to the ledger.
  3. Update `README.md`, `artifacts/sprint-3/workers/S3.8-A1.md`, and `artifacts/sprint-3/handoffs/S3.8-A1.md` to remove the assertion that distinct references cannot be distinguished or verified under the supported format. Clarify that while the bank format has no dedicated `REF:` field, reference identifiers in `ND:` distinguish transactions and prevent duplicate warnings.

### Finding 2: Robustness Gap — Platform Call `activeNotifications` Lacks Defensive Null Check (LOW / Actionable Quality)
- **Claim:** In `BankNotificationListener.kt:224`, `activeNotifications` is called directly without defensive null handling before converting to a list.
- **Evidence:**
  - `BankNotificationListener.kt:224-226`:
    ```kotlin
    val active = activeAnswer?.invoke() ?: activeNotifications
    reconcileActivePosts(
        active = active.toList(),
        accessGranted = true,
        allowedPackages = snapshot,
    )
    ```
- **Why It Matters:** In the Android SDK, `NotificationListenerService.getActiveNotifications()` returns a Java array `StatusBarNotification[]!`. On certain Android OEM distributions, during early initialization, or when the system service unbinds asynchronously, `getActiveNotifications()` can return `null` instead of an empty array. Calling `active.toList()` on `null` throws a `NullPointerException`, crashing the background reconciliation coroutine during `onListenerConnected()`.
- **Confidence:** HIGH.
- **Actionable Target (Source change recommended now):**
  Change to defensive null check:
  ```kotlin
  val active = activeAnswer?.invoke() ?: activeNotifications ?: emptyArray()
  ```

## 4. Differential Privacy, Storage & Security Architecture

### 4.1 Strict Allowlist Short-Circuiting
`decideNotificationIntake` enforces privacy order before touching content:
```kotlin
if (!isIntakePermitted(accessGranted = true, allowedPackages = allowedPackages, packageName = notification.packageName)) {
    return NotificationIntakeDecision.NotPermitted
}
return screenContent(notification.notification)
```
Because `notification.packageName` is platform metadata, non-approved packages never trigger bundle extraction or text reads. `ContentReadProbe.java` in tests confirms that `getNotification()` is invoked exactly 0 times for non-allowlisted apps.

### 4.2 Sensitive Body and Balance Exclusion
The database schema (`pending_bank_drafts`, Room version 5) contains 32 explicit columns:
- Routing provenance: `deliveryId`, `sourcePackage`, `notificationKey`, `postedAtEpochMillis`.
- Parsed fields: `bank`, `parseStatus`, `amountState`, `amountVnd`, `amountUnresolvedReason`, `direction`, `momentState`, `statedDate`, `statedTime`, `momentUnresolvedReason`, `memoState`, `memo`, `memoUnresolvedReason`.
- Digest and lifecycle: `evidenceDigest`, `reviewStatus`, `confirmedTransactionId`, `possibleDuplicateOfDraftId`, `createdAtEpochMillis`.
- Review overrides: `reviewAmountText`, `reviewDateText`, `reviewTimeText`, `reviewMemo`, `reviewMemoEdited`, `reviewType`, `reviewCategoryId`, `reviewCategoryResolved`, `reviewRevision`.

**Zero Sensitive Residue:** No raw notification title, text, or big-text is stored. Account numbers (`TK:`) and balance figures (`SDC:`) are completely excluded from storage. Neither `NotificationIntake.kt` nor `BankNotificationListener.kt` contains logging invocations (`android.util.Log`, `println`, `Logger`, or `Timber`).

### 4.3 Deduplication & Identity Guarantees
Intake identity splits platform delivery from evidence statement:
1. `deliveryId`: `"<pkg>|key:<key>|<postedAtEpochMillis>"` (or `"<pkg>|nokey|<postedAtEpochMillis>"`).
2. `evidenceDigest`: SHA-256 over length-prefixed canonical values of 13 permitted fields.
3. Unique index: `Index(value = ["deliveryId", "evidenceDigest"], unique = true)`.

If the identical notification is replayed or re-read upon reconnect, `storedDraftId` returns the existing row ID, performing no database insert and mutating no state. If a later post reuses the key with identical content, `PendingBankDraftDao` inserts a new draft and flags it with `possibleDuplicateOfDraftId = earliestDraftId`. Neither draft is silently discarded or merged.

### 4.4 Atomic Review Boundary
Confirmation in `BankDraftReviewDao.confirm` is wrapped in `@Transaction`:
1. Optimistically updates draft status to `CONFIRMED` conditioned on `reviewStatus = 'PENDING'`, `reviewRevision = :expectedRevision`, and `confirmedTransactionId IS NULL`.
2. Inserts a record into the `transactions` table.
3. Links the new transaction ID to `confirmedTransactionId`.
4. If any step fails or another thread already claimed the draft, the transaction rolls back cleanly.

When a confirmed transaction is deleted from the ledger by the user, the foreign key constraint:
```kotlin
ForeignKey(
    entity = TransactionEntity::class,
    parentColumns = ["id"],
    childColumns = ["confirmedTransactionId"],
    onDelete = ForeignKey.SET_NULL,
    onUpdate = ForeignKey.CASCADE,
)
```
sets `confirmedTransactionId` to `NULL`. However, `reviewStatus` remains `CONFIRMED`. As a result, subsequent callbacks cannot re-intake or re-confirm the deleted transaction.
