## 3. Technical Analysis

### 3.1 Main-Thread I/O Closure & Threading Model

In `app/src/main/java/io/github/triet4p/aegisf/notification/BankNotificationListener.kt:66-79`:

```kotlin
override fun onListenerConnected() {
    val appContext = applicationContext
    serviceScope.launch(ioDispatcher) {
        val loaded = NotificationAccessStore(appContext).loadAllowedPackages()
        if (!isActive) {
            return@launch
        }
        allowedPackages = loaded
        connectionState.value = ListenerConnection.Connected(System.currentTimeMillis())
    }
}
```

- **Evaluation:**
  - `onListenerConnected()` runs on `Looper.getMainLooper()` per AOSP platform architecture.
  - The method now captures `applicationContext` on the main thread and immediately launches an asynchronous coroutine on `ioDispatcher` (defaulting to `Dispatchers.IO`).
  - No storage I/O (`SharedPreferences.getStringSet()` / `awaitLoadedLocked()`) occurs on the caller thread, eliminating cold-start disk reads and avoiding `StrictMode.DiskReadViolation` or frame drops.
  - The previous incorrect comment claiming that listener callbacks run on a "system callback thread — never the Android main thread" has been completely removed and superseded by clear AOSP-accurate documentation (`BankNotificationListener.kt:34-41`).

### 3.2 Bind-Time Readiness Ordering & Callback Handling Analysis

In `BankNotificationListener.kt:88-109`:

```kotlin
override fun onNotificationPosted(notification: StatusBarNotification?) {
    // Not yet ready: undecided, never judged against the transient empty snapshot.
    // No permit/deny decision is made here; S3.7 reconciles active notifications.
    if (connectionState.value !is ListenerConnection.Connected) {
        return
    }
    val packageName = notification?.packageName ?: return
    if (!isIntakePermitted(
            accessGranted = true,
            allowedPackages = allowedPackages,
            packageName = packageName,
        )
    ) {
        return
    }
    // S3.1 ends here: an allowlisted package is recognised and nothing else happens.
    // No extras are read, nothing is logged, and nothing is stored.
}
```

- **Source Code vs. Worker Summary:**
  - In progress reports (P2), the worker explored awaiting the allowlist load (`loadJob.join()`) before evaluating callbacks. In the final artifact and handoff, the worker summarized the behavior as returning "undecided" on pre-ready callbacks.
  - Inspection of the actual source shows that `onNotificationPosted` is a `Unit`-returning Android service callback. When `connectionState.value !is ListenerConnection.Connected`, the callback executes an immediate `return`.
- **S3.1 Scope Assessment:**
  - In task S3.1, **no downstream intake exists**. Even when the listener is connected and a notification belongs to an allowlisted bank package, `onNotificationPosted` executes lines 107-108 and returns without taking any action. There is no transaction parsing, draft queue, or database write.
  - Returning early while not `Connected` guarantees that no notification is evaluated against the initial `emptySet()` default (avoiding a false-negative rejection against an uninitialized snapshot).
  - Therefore, within the boundary of task S3.1, no permitted notifications or intake data are dropped or lost.
- **Distinction Between Present Scope and Future Seam Risks:**
  - **Present Scope (S3.1):** The fail-closed early return is sound, minimal, and fully compliant with S3.1 requirements. It introduces no premature intake queuing or unnecessary concurrency abstractions.
  - **Future Seam Risk (S3.2 / S3.4 / S3.7):** When tasks S3.2 (intake filtering) and S3.4 (draft lifecycle) introduce real draft creation in `onNotificationPosted`, any notification arriving during the transient window between service binding and background allowlist loading would be skipped by `if (connectionState.value !is ListenerConnection.Connected) return`. Downstream tasks must ensure that:
    1. Active notifications present at bind time are reconciled via `getActiveNotifications()` as planned in S3.7 (`docs/sprint-plans/sprint-3.md:31`), OR
    2. S3.4 implements an intake dispatch queue that awaits allowlist availability.
  - This is an explicit architectural seam for upcoming tasks, not an actionable defect of S3.1.

### 3.4 Disconnect Cancellation & Scope Safety

In `BankNotificationListener.kt:81-86,115-118`:

```kotlin
override fun onListenerDisconnected() {
    serviceScope.coroutineContext.cancelChildren()
    connectionState.value = ListenerConnection.Disconnected
}

override fun onDestroy() {
    serviceScope.cancel()
    super.onDestroy()
}
```

- When the system unbinds the service upon access revocation, `serviceScope.coroutineContext.cancelChildren()` cancels any in-flight allowlist loading job without canceling the parent `SupervisorJob`.
- This ensures that:
  1. A cancelled load cannot publish a stale `ListenerConnection.Connected` or update `allowedPackages` after unbind.
  2. The service scope remains alive and capable of launching future loads if the service is rebound.
  3. `onDestroy()` cancels the parent scope completely.

## 7. External Prerequisites & Exact User-Run Next Steps

Because subagents cannot access a physical device or invoke `adb`, the following external verification steps MUST be performed by the user using the debug APK built at `app/build/outputs/apk/debug/app-debug.apk`:

### Step 1: Install Debug APK
Run via PowerShell or Terminal:

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

### Step 2: Verify Initial Settings State & Restricted Settings Resolution
1. Launch **Aegis F** on the phone.
2. Tap **Bank notifications** on the home screen.
3. Observe initial status:
   - `Notification access: Not granted`
   - `Listener: Listener not connected`
   - `Bank apps listed: 0 packages`
4. Tap **Open notification settings**.
   - If the toggle switch for Aegis F is disabled/greyed out ("Restricted setting" on Android 13/14+):
     - Tap **Back** into Aegis F, then tap **Open app info**.
     - In the system App Info page, tap the top-right 3-dot menu (`⋮`).
     - Tap **Allow restricted settings** and confirm with device PIN/fingerprint.
     - Return to Aegis F and tap **Open notification settings** again.
5. Turn ON the switch for **Aegis F** and tap **Allow** on the system confirmation dialog.
6. Return to Aegis F and observe the screen status update on resume:
   - `Notification access: Granted`
   - `Listener: Listener connected` (system server has bound the service).

### Step 3: Verify Bank App Allowlist & Intake Ready Status
1. Tap **Add a bank app**.
2. Type an invalid name (e.g. `VietinBank` or `bank`) and tap **Add**. Confirm it is refused with an error message and nothing is added.
3. Type the real application ID: `com.vietinbank.ipay` and tap **Add**.
4. Confirm `com.vietinbank.ipay` appears in the list with status **Ready**.

### Step 4: Verify Revocation State Update
1. Open the phone's system **Settings** → **Apps** → **Special app access** → **Device & app notifications** (or tap **Review notification access** inside Aegis F).
2. Turn OFF notification access for Aegis F.
3. Return to Aegis F and observe the status update on resume:
   - `Notification access: Not granted`
   - `com.vietinbank.ipay` status changes to **Waiting for access**.

### Step 5: Verify Manual Recording Independence
1. From the home screen, tap **Record a transaction**.
2. Record an expense (e.g. 50,000 VND under Food).
3. Confirm the transaction is saved, visible in **Saved transactions**, and correctly tallied in the **THIS MONTH** card.
4. Verify that manual recording operates without error regardless of whether notification access is granted or revoked.
