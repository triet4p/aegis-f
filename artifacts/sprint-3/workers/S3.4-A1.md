### Schema/API handoff for S3.5/S3.6

- **Table `pending_bank_drafts`:** `id`, `sourcePackage`, `notificationKey?`, `postedAtEpochMillis`, `bank` (`VIETINBANK` | `UNSUPPORTED`), `parseStatus` (`PARSED` | `UNSUPPORTED_FORMAT`), `amountState` + `amountVnd?` + `amountUnresolvedReason?`, `direction` (`DEBIT` | `CREDIT` | `UNKNOWN`), `momentState` + `statedDate?` + `statedTime?` (`YYYY-MM-DD`/`HH:mm`, no zone) + `momentUnresolvedReason?`, `memoState` + `memo?` + `memoUnresolvedReason?` (`UNREADABLE` | `REDACTED` | `AMBIGUOUS`), `reviewStatus` (`PENDING` — intake writes nothing else), `confirmedTransactionId?` (FK → `transactions.id`, `SET_NULL`), `createdAtEpochMillis`. Indices on `reviewStatus` and `confirmedTransactionId`.
- **S3.5 (dedup):** key provenance available as (`sourcePackage`, `notificationKey`, `postedAtEpochMillis`) plus parsed fields; no dedup heuristics implemented here — repeated callbacks currently store repeated rows. Preserve `DISMISSED`/`CONFIRMED` identity against replay when building it.
- **S3.6 (review):** read via `IntakeRepository.drafts()` / `observeDrafts()`; on explicit user confirmation convert (`statedDate`, `statedTime`) via `ManualDateTime.toEpochMillis` under the documented device-zone policy, write the ledger record, and set `confirmedTransactionId` + `reviewStatus = CONFIRMED` atomically (single-confirmation guard belongs there); `DISMISSED` likewise writes no ledger row. Never derive a ledger type from `direction` without the user's explicit choice.
- **S3.7 (recovery):** drafts are recovered via `observeDrafts()`; the init queue is memory-only and cleared on revoke/destroy — active-notification reconciliation must not treat it as history.
