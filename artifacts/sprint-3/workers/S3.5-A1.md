### Identity rules and schema/API handoff for S3.6/S3.7

- **Rule 1 — delivery identity.** `deliveryId = draftDeliveryId(sourcePackage, notificationKey)` = `"<package>|key:<notificationKey>"`, or `"<package>|nokey"` when the platform supplies no key. It is persisted (not recomputed) so the constraint, the listener, and any later reconciliation agree. It names a notification slot, never a transaction.
- **Rule 2 — evidence digest.** `evidenceDigest = draftEvidenceDigest(bank, parseStatus, amountState, amountVnd, amountUnresolvedReason, direction, momentState, statedDate, statedTime, momentUnresolvedReason, memoState, memo, memoUnresolvedReason)` — SHA-256 over a length-prefixed, `\u001F`-separated canonical form with `n` for an absent value. Delivery metadata (`sourcePackage`, `notificationKey`, `postedAtEpochMillis`), storage metadata (`createdAtEpochMillis`), and the review lifecycle (`reviewStatus`, `confirmedTransactionId`, `possibleDuplicateOfDraftId`) are deliberately excluded, so a re-post at another time and an update carrying the same statement produce the same digest, while any changed amount, direction, date/time, memo, state, or unresolved reason does not. It is derived from the row's own fields at construction (`PendingBankDraftEntity.evidenceDigest` default) and stored; a `copy` that changes evidence must re-stamp it, and no intake path rewrites a stored row.
- **Rule 3 — replay.** Same `deliveryId` **and** same `evidenceDigest` ⇒ the delivery is already stored ⇒ nothing is written and `storePermitted` returns that existing draft id, whatever review state it holds (`PENDING`, `CONFIRMED`, or `DISMISSED`). Enforced by the unique index `index_pending_bank_drafts_deliveryId_evidenceDigest` through `INSERT OR IGNORE`, inside Room's transaction, so concurrency, a crash between lookup and insert, and a second process cannot slip a duplicate through.
- **Rule 4 — changed statement, same slot.** Same `deliveryId`, different `evidenceDigest` ⇒ a new `PENDING` draft is inserted and **no stored row is updated**; the earlier draft keeps its values, its review state, and its ledger link. This is what keeps a reused notification key from erasing a real transaction, and it is deliberately *not* flagged as a possible duplicate (the evidence differs; treating a reused slot's later statement as a duplicate of an unrelated earlier one would be a guess the sprint forbids).
- **Rule 5 — uncertain cross-notification duplicate.** Different `deliveryId`, identical `evidenceDigest` ⇒ both rows are kept and the later one gets `possibleDuplicateOfDraftId` = `MIN(id)` of the already-stored rows with that digest (the earliest matching statement, stable as more arrive). Never merged, never deleted, never auto-collapsed.
- **Rule 6 — no reference-based collapse.** See reference provenance below: no supported format states a transaction reference, so equal evidence across deliveries is only ever *flagged*, never fused. If S3.8 device evidence reveals a stated reference, the change is a real one — a parsed evidence field (stated/unresolved), inclusion in the digest, and a strong-identity branch that may then collapse instead of flag; **no plug-in seam or future-API placeholder was added for it**, and no reference is derived from the memo, the account line, the balance, or the notification key.
- **Table `pending_bank_drafts` (schema version 3):** `id`; `deliveryId` NOT NULL; `sourcePackage`; `notificationKey?`; `postedAtEpochMillis`; `bank` (`VIETINBANK` | `UNSUPPORTED`); `parseStatus` (`PARSED` | `UNSUPPORTED_FORMAT`); `amountState` + `amountVnd?` + `amountUnresolvedReason?`; `direction` (`DEBIT` | `CREDIT` | `UNKNOWN`); `momentState` + `statedDate?` + `statedTime?` + `momentUnresolvedReason?`; `memoState` + `memo?` + `memoUnresolvedReason?`; `evidenceDigest` NOT NULL; `reviewStatus` (`PENDING` — intake writes nothing else); `confirmedTransactionId?` (FK → `transactions.id`, `SET_NULL`); `possibleDuplicateOfDraftId?` (self-FK → `pending_bank_drafts.id`, `SET_NULL`); `createdAtEpochMillis`. Indices: unique `(deliveryId, evidenceDigest)`, `evidenceDigest`, `possibleDuplicateOfDraftId`, `reviewStatus`, `confirmedTransactionId`.
- **API:** `IntakeRepository.storePermitted(sourcePackage, notificationKey, postedAtEpochMillis, content): Long` (idempotent; returns the existing draft id on replay), `drafts()`, `observeDrafts()` unchanged in shape. `PendingBankDraftDao.store(draft): Long` is the only write path; `insertIgnoringStoredIdentity`, `storedDraftId`, and `earliestDraftWithEvidence` are `protected` implementation details.
- **S3.6 (review inbox):** read drafts via `drafts()` / `observeDrafts()`; a non-null `possibleDuplicateOfDraftId` is the consumer-ready "may be the same transaction as draft #N" flag (resolve the partner with `findById`); `evidenceDigest` groups all rows stating one statement. Confirmation must stay a single atomic transaction (write the ledger record, then set `reviewStatus = CONFIRMED` **and** `confirmedTransactionId`), convert (`statedDate`, `statedTime`) via `ManualDateTime.toEpochMillis` under the documented device-zone policy, and never derive a ledger type from `direction`; dismissal sets `reviewStatus = DISMISSED` with no ledger row. Because intake never updates a row, a confirmation or dismissal cannot be reverted by a later delivery — a changed statement under the same slot arrives as a separate `PENDING` draft the inbox shows next to the reviewed one. If S3.6 deletes drafts, `possibleDuplicateOfDraftId` links to them clear themselves (`SET_NULL`).
- **S3.7 (recovery):** a reconciled or re-read active notification is idempotent through the same pair (same key + same evidence ⇒ no write), so reconciliation cannot double-store; a notification whose payload the bank changed while it was active will legitimately appear as its own `PENDING` draft beside the earlier one. The init queue stays memory-only and cleared on revoke/destroy; already-persisted drafts, their ids, and the migrated identities survive restart.

The stored row keeps its own `postedAtEpochMillis` as provenance; distinguishing that case needs device evidence (a stated reference), which S3.8 may supply.
