### Outcome

- **Status:** `implementation_complete` for reachable S3.6 code and host-side behavior. Device/UI interaction was unavailable and is not claimed; the outstanding natural-delivery/privacy/device checks remain S3.8.
- **Home entry point:** **Review bank drafts** opens the live pending inbox. Each row shows bank/unsupported attribution, source package, bank-stated date/time, amount, bank direction, memo, parse/review status, and unresolved reasons. Possible-duplicate rows show a warning and a button to the related draft with its current Pending/Confirmed/Dismissed state. Opening an earlier row also reveals later flagged candidates.
- **Review actions:** the detail screen keeps parsed bank evidence visible and permits editable amount/date/time/optional description. Expense, Income, or Internal transfer starts unselected; a debit/credit never chooses a ledger type. Expense/income requires an explicit category or **No category** choice; transfers have no category. Amount/date/time/type/applicable-category issues are shown and rejected before confirmation. An unknown memo stays visibly unresolved and may remain blank. The date/time notice says the bank supplied an unzoned wall clock; only confirmation converts it under the app's current device-zone policy.
- **Persistence/API:** `BankDraftReviewRepository.saveReview`, `confirmDraft`, and `dismissDraft` use a monotonic `reviewRevision` compare-and-set. User overrides are separate from parsed source fields and `evidenceDigest`; S3.5 delivery/evidence replay identity is unchanged. Schema v5 adds review amount/date/time/memo/type/category fields and the revision, with migration 4→5 adding nullable overrides and zero-default flags/revision. No destructive migration fallback was added.
- **Atomic guarantee:** `BankDraftReviewDao.confirm` runs as one Room transaction: it checks the current pending state/revision and active category, conditionally claims the draft as Confirmed, inserts one confirmed `BANK_NOTIFICATION` ledger row, then links it. Any insert/link failure rolls the claim back. Repeated/concurrent confirms and stale confirms after dismissal/confirmation cannot insert; dismissal makes only a conditional terminal status update and writes no ledger row. Deleting the linked transaction keeps the draft terminal (`ON DELETE SET NULL`); replay still resolves to the stored terminal delivery and does not recreate the deleted transaction.
- **Changed files:** `MainActivity.kt`; new `ui/BankDraftReviewScreen.kt`; new `data/BankDraftReviewDao.kt` and `data/BankDraftReviewRepository.kt`; `data/PendingBankDraftEntity.kt`, `PendingBankDraftDao.kt`, `LedgerDatabase.kt`, `AppContainer.kt`; `notification/NotificationIntake.kt` (obsolete parser-timing KDoc corrected); new `data/BankDraftReviewTest.kt`; `data/PendingBankDraftMigrationTest.kt`; generated `app/schemas/io.github.triet4p.aegisf.data.LedgerDatabase/5.json`; `README.md`; `CHANGELOG.md`.
