### Identity rules and schema/API handoff for S3.6/S3.7

- **Rule 1 — delivery identity.** `deliveryId = draftDeliveryId(sourcePackage, notificationKey, postedAtEpochMillis)` = `"<package>|key:<notificationKey>|<postedAt>"`, or `"<package>|nokey|<postedAt>"` when the platform supplied no key. It is persisted (not recomputed at read time) and names one platform **post**, never a transaction. It is injective: the post time is a decimal integer, so it carries no `|` and the last segment always splits off as the post time.
- **Rule 2 — evidence digest.** `evidenceDigest = draftEvidenceDigest(bank, parseStatus, amountState, amountVnd, amountUnresolvedReason, direction, momentState, statedDate, statedTime, momentUnresolvedReason, memoState, memo, memoUnresolvedReason)` — SHA-256 over a length-prefixed, `\u001F`-separated canonical form with `n` for an absent value. Delivery metadata (`sourcePackage`, `notificationKey`, `postedAtEpochMillis`), storage metadata (`createdAtEpochMillis`), and the review lifecycle (`reviewStatus`, `confirmedTransactionId`, `possibleDuplicateOfDraftId`) are excluded by construction.
- **Rule 3 — replay.** Same `deliveryId` **and** same `evidenceDigest` ⇒ already stored ⇒ nothing is written and `storePermitted` returns that existing draft id, whatever review state it holds (`PENDING`, `CONFIRMED`, or `DISMISSED`). Enforced by the unique index `index_pending_bank_drafts_deliveryId_evidenceDigest` through `INSERT OR IGNORE` inside Room's transaction.
- **Rule 4 — later post under a reused key.** Different `deliveryId` (the post time differs), identical `evidenceDigest` ⇒ a new `PENDING` draft is inserted, flagged `possibleDuplicateOfDraftId` = `MIN(id)` of the already-stored rows with that digest; no stored row is updated. This is the corrected case: the earlier rule dropped this delivery as a replay and lost a real transaction.
- **Rule 5 — changed statement under a reused key.** Different `deliveryId`, different `evidenceDigest` ⇒ a new `PENDING` draft, **not** flagged (a different stated statement is not a candidate twin; key reuse alone is never identity).
- **Rule 6 — uncertain cross-notification duplicate.** Different `deliveryId`, identical `evidenceDigest` ⇒ both rows kept, the later flagged at the earliest matching statement. Never merged, never deleted, never auto-collapsed.
- **Rule 7 — no reference-based collapse.** No supported format states a transaction reference (evidence below), so no reference column or reference-extraction seam exists; equal evidence is only ever flagged.
- **Table `pending_bank_drafts` (schema version 4, structurally identical to version 3):** `id`; `deliveryId` NOT NULL (post identity); `sourcePackage`; `notificationKey?`; `postedAtEpochMillis`; `bank` (`VIETINBANK` | `UNSUPPORTED`); `parseStatus` (`PARSED` | `UNSUPPORTED_FORMAT`); `amountState` + `amountVnd?` + `amountUnresolvedReason?`; `direction` (`DEBIT` | `CREDIT` | `UNKNOWN`); `momentState` + `statedDate?` + `statedTime?` + `momentUnresolvedReason?`; `memoState` + `memo?` + `memoUnresolvedReason?`; `evidenceDigest` NOT NULL; `reviewStatus` (`PENDING` | `CONFIRMED` | `DISMISSED`); `confirmedTransactionId?` (FK → `transactions.id`, `SET_NULL`); `possibleDuplicateOfDraftId?` (self-FK, `SET_NULL`); `createdAtEpochMillis`. Indices: unique `(deliveryId, evidenceDigest)`, `evidenceDigest`, `possibleDuplicateOfDraftId`, `reviewStatus`, `confirmedTransactionId`.
- **Migrations:** `MIGRATION_1_2` (create the drafts table), `MIGRATION_2_3` (rebuild with the two identity columns and the duplicate link, deriving them from the row's own provenance including its post time; the copy keeps the earliest row of each derived identity, so a version-2 file that stored one delivery repeatedly upgrades instead of failing on the unique index), `MIGRATION_3_4` (re-derive `deliveryId` for every stored row from `sourcePackage`/`notificationKey`/`postedAtEpochMillis`; no DDL, no row loss, idempotent). No destructive fallback anywhere.
- **API:** `IntakeRepository.storePermitted(sourcePackage, notificationKey, postedAtEpochMillis, content): Long` (idempotent per post+statement; returns the existing draft id on replay), `drafts()`, `observeDrafts()` unchanged in shape. `PendingBankDraftDao.store(draft): Long` is the only write path; `insertIgnoringStoredIdentity`, `storedDraftId`, and `earliestDraftWithEvidence` are `protected` implementation details.
- **S3.6 (review inbox):** read drafts via `drafts()` / `observeDrafts()`; a non-null `possibleDuplicateOfDraftId` is the consumer-ready "may be the same transaction as draft #N" flag (resolve the partner with `findById`) and now also covers a later real transaction under a reused key; `evidenceDigest` still groups all rows stating one statement, and two rows may share it. Confirmation must stay a single atomic transaction (write the ledger record, then set `reviewStatus = CONFIRMED` **and** `confirmedTransactionId`), and must never reopen or mutate another row.
- **S3.7 (recovery):** a re-read active notification re-delivers the same post (same key, same post time) and is idempotent through the pair; a notification whose payload the bank changed while it was active appears as its own `PENDING` draft beside the earlier one. The init queue stays memory-only and is cleared on revoke/destroy; already-persisted drafts, their ids, and the migrated identities survive restart and the version-3 upgrade.
