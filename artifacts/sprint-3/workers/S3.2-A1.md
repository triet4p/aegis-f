### Rejected vs accepted semantics (what the boundary actually decides)

- **Not permitted** (package first): package name is not an exact allowlist entry, or the allowlist is empty. Nothing about the notification's title, text, big text, or extras is read, so no body can influence the outcome — `ContentReadProbe.contentReads()` is 0 in every such case.
- **Rejected / `SecurityContent`**: an OTP, verification code, login or new-device alert, password instruction, or the "do not share" wording banks send with them, matched in English and Vietnamese wording. The decision carries the reason only, so no security body is retained anywhere.
- **Rejected / `GroupSummary`**: the notification carries `FLAG_GROUP_SUMMARY`; it aggregates other notifications, so there is no single event to intake. Rejected before any text field is read.
- **Rejected / `NoContent`**: every supported field is absent or whitespace.
- **Rejected / `RedactedOnly`**: masked values, redaction words, and bare `GD:`/`TK:`/`ND:`-style labels are removed and nothing readable remains — `........`, `****`, `xxxx xxxx`, `[redacted]`, `TK: Redacted` with `ND: ........`.
- **Permitted (candidate only)**: at least one supported field still carries a digit or a word after redaction is discounted. The user's VietinBank sample is exactly this case: `TK: Redacted` and `ND: ........` are preserved verbatim beside the readable `GD: -50,000 VND`, so the partially redacted message stays usable for the later parser. A permitted decision holds no amount, direction, date, or confirmation and is never counted as a successful transaction.

### Privacy boundaries held

- Package before content: the allowlist comparison uses `StatusBarNotification.getPackageName()` only; the content object is obtained inside the boundary strictly after that check passes.
- No message body or account identifier is logged: the changed production files contain no logging call at all, and the decision type for a rejection has no field capable of carrying text.
- No retention: no SharedPreferences write, no Room write, no in-memory queue, no cached content. The listener discards the decision; S3.3/S3.4 consume it later at that same seam.
- Readiness: a post arriving before the allowlist load completes returns before the package name and content are read, so a transient empty snapshot can neither deny a permitted package nor trigger a content read. Revocation (`onListenerDisconnected`) drops the in-flight load and returns the listener to `Disconnected`, after which no post is processed.
- Bind-window obligation documented rather than overstated: the window before readiness is a miss, not captured history and not queued for replay; the listener's documentation records that S3.4 must feed this seam into the pending-intake queue and S3.7 must reconcile what is still active on the system side. No missed-history capture is claimed.
- Out of scope and untouched: bank parser, draft database/lifecycle, deduplication/inbox, ledger, manifest permissions, and the settings UI.
