## Why this attempt exists

Main's acceptance finding on S3.5-A1: its own artifact admitted that a **later real transaction reusing the same notification key with byte-identical permitted evidence is discarded as a replay**. The user's sample has minute-resolution time, a redacted account line, a masked memo, and **no** transaction reference, so two real 50,000 VND transactions inside one minute are indistinguishable by parsed evidence — and the delivery identity `pkg|key` (or `pkg|nokey`) plus `evidenceDigest` ignored the already-available `postedAtEpochMillis` provenance, so the second delivery collided with the first and was dropped. Documenting that loss was explicitly not acceptance; the criterion is that "distinct equal-value transactions [are not] collapsed merely because amount/time are similar".

**Had the old identity already been post-scoped?** No. Evidence read in `PendingDraftIdentity.kt` (pre-correction): `draftDeliveryId(sourcePackage, notificationKey)` produced `"<pkg>|key:<key>"` / `"<pkg>|nokey"` only, and the unique index `(deliveryId, evidenceDigest)` therefore keyed a delivery by the notification slot, not by the post. `IntakeRepository.storePermitted` already received `postedAtEpochMillis` (the listener passes `StatusBarNotification.postTime`) and stored it as provenance, but it was neither part of the constraint nor of the digest — so a later post under a reused key with identical parsed evidence was structurally indistinguishable from a replay.

## Exact identity and schema contract

1. **Delivery identity (persisted, not recomputed):** `deliveryId` = `"<package>|key:<notificationKey>|<postedAtEpochMillis>"`, or `"<package>|nokey|<postedAtEpochMillis>"` when the platform supplied no key. It names one platform **post**.
2. **Evidence digest (persisted, derived at construction):** SHA-256 over the length-prefixed `\u001F`-separated canonical form of `bank`, `parseStatus`, `amountState`, `amountVnd`, `amountUnresolvedReason`, `direction`, `momentState`, `statedDate`, `statedTime`, `momentUnresolvedReason`, `memoState`, `memo`, `memoUnresolvedReason`; `n` marks an absent value. No delivery metadata, no review lifecycle, no raw body.
3. **Constraint:** unique index `index_pending_bank_drafts_deliveryId_evidenceDigest` on `(deliveryId, evidenceDigest)`; `store()` = transactional replay lookup → earliest identical-evidence anchor → `INSERT OR IGNORE` → race fallback; nothing is ever updated or `REPLACE`d.
4. **Same post + same evidence ⇒** no write, return the stored draft id in whatever review state it holds.
5. **Later post under a reused key + identical evidence ⇒** new `PENDING` row, `possibleDuplicateOfDraftId` = `MIN(id)` of rows with that digest; all earlier rows untouched. (This is the corrected loss case.)
6. **Different post + different evidence ⇒** new `PENDING` row, **not** flagged (key reuse alone is not identity).
7. **Missing key ⇒** identity is package + post time; independent keyless deliveries are never collapsed, only flagged when their evidence matches.
8. **Terminal rows are immutable:** `CONFIRMED`/`DISMISSED` state and `confirmedTransactionId` never revert or mutate through a replay or a later identical post; the later delivery becomes its own flagged candidate and writes no ledger row.
9. **Schema version 4** = version 3 structure. `MIGRATION_2_3` derives identities with the post time and keeps the earliest row of each derived identity (version 2 stored every callback, so a file may hold one delivery more than once; copying the exact duplicate would make the unique index impossible to create); `MIGRATION_3_4` rewrites only the `deliveryId` values of already-stored rows, from their own stored provenance, preserving ids, values, review states, ledger links, and duplicate links. Neither rewrite can violate the unique index: version 3 already allowed at most one row per `(package, key, evidence)`, and rows sharing a key keep distinct digests. No destructive fallback.

## Additional defect found while verifying, and fixed (not the assigned finding)

The version-2 → version-3 migration was re-read end to end, and a crash path was found and fixed. Version 2 (`S3.4`) had no identity constraint at all: every permitted callback stored its own row, so a version-2 database can hold byte-identical rows for one delivery (a post delivered once before readiness and once after, or a replayed callback). `MIGRATION_2_3` copied *every* row into the rebuilt table and created the unique `(deliveryId, evidenceDigest)` index only afterwards, so such a pair would have made the index creation fail — SQLite refuses a unique index over duplicate key values — and, with no destructive fallback, the upgrade would have surfaced as a failed database open.

- **Fix:** the copy now reads the rows in id order and keeps the first row of each derived identity, then inserts the kept rows and creates the indices as before. The kept row is the one the running app's own store would have kept (a repeated delivery of one identity writes nothing, and the existing possible-duplicate anchor is `MIN(id)`), and no row that is not an exact duplicate delivery is touched.
- **Why this is not an invented data policy:** a version-2 draft could only ever be `PENDING` with a null `confirmedTransactionId` (version 2 shipped no review transition — no status API existed until S3.6, which is still unbuilt), so nothing reviewed can be collapsed; rows sharing a key but differing in post time or evidence are all copied; migrated rows still get no invented duplicate link.
- **Regression:** `a version two database with repeated callbacks upgrades without failing or duplicating` — a real version-2 file with ids 7 and 8 holding the same delivery and id 9 holding a later post under the same reused key upgrades through the production builder to exactly rows 7 and 9, with `PRAGMA user_version = 4`, replay of that delivery returning id 7, and the ledger row and id preserved.
- **Alternatives rejected:** creating the unique index before the copy and inserting with `INSERT OR IGNORE` (SQLite applies `OR IGNORE` to every constraint, so a row with a dangling ledger link would be dropped silently instead of failing loudly as it does today); dropping the unique index so every legacy row survives (it is the table-level guarantee the S3.5 tests rely on); keeping the copy as it was and letting the upgrade fail (an unusable app on a real device).

## Failed / rejected approaches

- **Keep `(pkg|key, digest)` and only surface a review hint.** Rejected: the later real transaction would still be discarded, which is exactly the acceptance finding — presentation cannot fix a storage decision.
- **Repin identity strings without touching stored rows.** Rejected: already-created version-3 databases would stop recognizing their own replays and would duplicate drafts after upgrade. Hence `MIGRATION_3_4` re-deriving every stored `deliveryId`.
- **Fuzzy time window ("same transaction if post times are within N minutes").** Rejected: an invented threshold with no evidence behind it, and it is precisely the "similar time" collapse the sprint forbids.
- **Fold the post time into `evidenceDigest`.** Rejected: the digest defines "the same *statement*", and every consumer (possible-duplicate lookup, S3.6 grouping) needs it to group identical statements across deliveries; delivery provenance belongs in the delivery identity.
- **Add a bank transaction-reference column / reference extraction.** Rejected in S3.5-A1 and still rejected: the user's sample states no reference and the bank-context boundaries forbid deriving one from `TK`/`SDC`/`ND`; that would be dead scaffolding for an unobserved format.
- **Drop the unique constraint and deduplicate only via lookups.** Rejected: it would lose the table-level guarantee that concurrent callbacks (or a crash between lookup and insert) cannot store a duplicate; the tests keep that constraint exercised.
- **Version bump without a migration, or `fallbackToDestructiveMigration`.** Rejected: either loses stored draft ids, review states, and ledger links.
- **Use `Notification.when` (bank-set) as the discriminator.** Not used: it is not persisted anywhere today and was never observed; `postedAtEpochMillis` is the platform metadata the row already stores.
- **Invent a per-delivery counter/UUID for keyless posts.** Rejected: an invented identifier would make a genuine replay of the same keyless post non-idempotent; the platform post time is real provenance.
- **Retire the loss-encoding tests by repinning their expected strings.** Rejected: the three tests asserted the loss itself, so they were rewritten to assert the corrected consumer-visible behavior instead.
