### The exact API contract behind Finding 2 (checked, not assumed)

The review attributed the null to "certain Android OEM distributions". The source says something narrower and checkable, and this attempt reports that instead:

| Platform source | `getActiveNotifications()` body | Result on an unbound listener |
| --- | --- | --- |
| `android-7.0.0_r1` (API 24, this app's `minSdk`) | `return getActiveNotifications(null, TRIM_FULL)` | **null** — the inner overload returns null when `!isBound()`, and the public method passes it straight through |
| `android-8.1.0_r1` (API 27) | `return getActiveNotifications(null, TRIM_FULL)` | **null** (same) |
| `android-9.0.0_r1` (API 28) | `activeNotifications != null ? activeNotifications : new StatusBarNotification[0]` | empty array |
| `android-10.0.0_r1` (API 29) | `activeNotifications != null ? activeNotifications : new StatusBarNotification[0]` | empty array |
| `android-14.0.0_r1` (API 34, the Robolectric SDK these tests run on) | `activeNotifications != null ? activeNotifications : new StatusBarNotification[0]` | empty array |

So the null is a documented platform behavior of API 24–27 — a supported range, since the module sets `minSdk = 24` — and the fix is a correctness fix for that range, not a defensive guess. Robolectric's `ShadowNotificationListenerService` substitutes an empty array exactly as API 28+ does, which is why the regression supplies the unavailable answer through the listener's existing answer seam rather than pretending the shadow can produce it.
