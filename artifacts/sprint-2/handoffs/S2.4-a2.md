## Key findings and decisions

1. Material3 1.4.0 sources read (official androidx-main mirrors) confirmed the row semantics: `SingleChoiceSegmentedButtonRow` = `Row(selectableGroup(), defaultMinSize(ContainerHeight), width(IntrinsicSize.Min), horizontalArrangement = spacedBy(-space), verticalAlignment = CenterVertically)`; each `SegmentedButton` = `Surface(Modifier.weight(1f).defaultMinSize(...))` with label content measured per-button. `Surface(selected, onClick)` uses `Modifier.selectable` (so the segment semantics node carries `Selected`, `onClick`, and merged label text — matched reliably with `hasText(label) and hasClickAction()`).
2. Compose BOM 2026.09.00 resolves Compose UI test to version 1.12.1 (material3 1.4.0). API drift handled so far: `onAllNodes`/`onNode` are members of the test provider, `onNodeWithText` is a top-level extension, `Offset` fields are Float, `SemanticsConfiguration` has `getOrElse`, not `getOrNull`.
3. `createComposeRule()` in 1.12.1 is deprecated in favor of the `androidx.compose.ui.test.junit4.v2` variant (warning only).
4. Font scale on the Robolectric host: `RuntimeEnvironment.setFontScale` exists in the pinned Robolectric 4.17 (verified by javap of `shadows-framework-4.17.jar`), but `@BeforeClass` application is reset per method (`RuntimeEnvironment.getFontScale()` printed 1.0 in the "enlarged" run), so the enlarged-font numbers below are NOT proof of 1.5x. Current approach: provide the enlarged density explicitly at composition via `CompositionLocalProvider(LocalDensity provides Density(density, 1.5f))` and record `LocalDensity.current.fontScale` from inside the composition (`effectiveScale` var) — pattern endorsed by Main; NOT yet compiled/observed.
5. Label-fit check must not rely on unmerged Text-node bounds (they printed nonsensical `left=160 right=168` widths, i.e. 8 px, so that assertion was vacuous). `TextLayoutResult.hasVisualOverflow` was intended, but the `getTextLayoutResult` top-level function does not exist in ui-test 1.12.1 (verified by javap: only `BoundsAssertionsKt` mentions `TextLayoutResult`; `TextActionsKt`/`SemanticsNodeInteraction` have no such member). Next safe route (choose one, simplest first):
   a. Invoke the semantics action directly: the Text node carries `SemanticsActions.GetTextLayoutResult`; fetch it from `node.config` and call it with a callback to obtain the `TextLayoutResult`, then assert `!hasVisualOverflow`.
   b. If that is too awkward, prove label fit structurally instead: exact label text present on the segment + equal segment geometry + segment height ≥ content-driven (multiline) height for the Internal transfer label (line count > 1 at 320 dp), and defer the final "no clipping under 1.5x" statement to the ONE optional user visual recheck in the proof artifact (assignment allows stating an honest visual limit instead of fabricating proof).
