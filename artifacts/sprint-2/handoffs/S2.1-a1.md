### 2.3 Decisions taken (and why)

| Decision | Rationale |
| --- | --- |
| No sign column; `amountVnd` holds a positive magnitude only, direction comes from `type` (`EXPENSE`/`INCOME`/`TRANSFER`) | Sprint/plan rule: "VND only: store amounts as signed 64-bit integer whole dong" and S2.1 "type determines financial direction". A separate sign column would allow contradictory rows. |
| `transactions.categoryId` is nullable, with `ON DELETE RESTRICT` + repository guard that refuses to delete a referenced category | Plan decision: "archived categories remain attached to historical records"; an unknown category must not prevent saving. RESTRICT plus a repository check makes historical links structurally safe. |
| `categories.name` uniqueness enforced only for **unarchived** names, via a query (`findActiveIdByName`) rather than a DB unique index | Archive semantics: an archived name may be reused by a new category (plan allows add/rename/archive; a hard unique index would block re-creation and would need a schema change later). Case-insensitive compare via `COLLATE NOCASE`. |
| `@Database(version = 1, exportSchema = true)`, `room.schemaLocation` = `app/schemas` | Schema versioning acceptance item; exported JSON is the migration reference. |
| No `fallbackToDestructiveMigration()` anywhere | Migration mistakes must not silently destroy the user's ledger. |
| Timestamps are `Long` epoch millis in the entity, produced by an injectable `LedgerClock` (`SystemLedgerClock` in production) | Host tests need deterministic times; no clock dependency on Android framework classes. |
| `ConfirmationStatus { CONFIRMED, DRAFT }` and `RecordSource { MANUAL, BANK_NOTIFICATION }` | Only confirmed expenses may enter totals (sprint acceptance) and notification-derived records must be identifiable (Sprint 3 draft intake). Both are data-only in S2.1 — no screen, no inference. |
| `LedgerRepository` returns entity rows directly rather than a separate domain model | Entities already are the storage shape; a parallel model would add mapping cost with no differing rule (rule "no needless abstraction"). |
| Validation lives in the repository, not the DAO | DAOs stay mechanical; the repository owns the storage/domain boundary the task names. `LedgerValidationException extends IllegalArgumentException`. |
| `AegisApplication` + `AppContainer(context)` (lazy DB + lazy repository) is the production entry point | Satisfies "production DB/repository has a real usable entry point, not a disconnected test-only schema". No UI is wired to it yet — deliberately, to avoid inventing Sprint 2.3+ screens. |
