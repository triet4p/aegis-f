## 5. Defect A — no-fail-fast policy not applied to the fresh assisted batch

- The batch stopped with `hard_stop: runtime_safety_stop:unexpected_or_financially_unsafe_link`
  after slot 6 and recorded the remaining 18 pass-1 cases as `not_run_safety_stop`; passes 2–3 were
  never started.
- Trigger: `a8-link-02`. Persisted state is
  `links: [{id: 1, event_id: 313, draft_id: 421, state: "PROPOSED"}]` with `verified_effects: []`,
  `ledger_rows: 0`, `out_of_scope_effect_rows: 0`, `unexpected_mutation_operations: 0`. The frozen
  mapping for that case pins `{event_id: 313, draft_id: 422, state: PROPOSED}` with
  `attachment_forbidden: true`. The candidate proposed the sibling duplicate and asked the user;
  **nothing was attached** and no financial effect occurred. The frozen rule nevertheless classifies
  any non-matching link row as `unexpected_or_financially_unsafe_link`
  (`S813QualificationInstrumentedTest.kt:452`).
- Harness mechanism: the run takes the batch stop from the case adjudication
  (`S813QualificationInstrumentedTest.kt:892-901`) when no exhaustive continuation is bound. Under
  the already owner-approved TEST_ONLY exhaustive no-fail-fast policy
  (`:894-896`, only an explicit `S813_EXHAUSTIVE_DECISION_STOP` stops the batch), an independent
  case's proposal mismatch does not stop the remaining cases. That policy was not applied to this
  fresh assisted batch, so one case's tentative sibling-duplicate proposal aborted 18 independent
  cases.
- This is the defect to fix. It is not evidence that the candidate performed an actual unsafe
  attachment, and it is not a request to redefine the frozen expected pair: the frozen raw evidence,
  the frozen rubric and the frozen mapping are preserved unchanged.
- Behavioural note only: the a63 first attempt on the earlier accepted snapshot (`ff787d9`) produced
  the identical tentative row (`draft_id: 421`, PROPOSED). The candidate consistently proposes the
  sibling duplicate; the defect is that the harness let that mismatch stop independent cases.

## 6. Defect B — assisted records cannot bind the host assisted scoring

- Device: `runAssistedStep` stores the continuation's raw record as `assisted_record` and the
  second-phase adjudication only as `assisted_adjudication`, with `cumulative_safety_ok`
  (`S813QualificationInstrumentedTest.kt:1519-1528`). The first record, by contrast, is annotated
  with `adjudication_version` / `financial_safety_match` / `quality_findings` (`:864-866`).
- Host: `assisted_evaluation` re-evaluates `record["assisted_record"]` through
  `evaluate_case(record_override=…)`, and `technical_success` requires
  `record.get("adjudication_version") == ADJUDICATION_VERSION`
  (`tools/slm/s8_agent_v3_qualification.py:1003`, `:6901-6906`, `:7048-7060`).
- Observed: both continuations' `assisted_record` lack those fields; the host path reports
  `adjudication_binding: false` and `technical_success: false`, so `recovered` can never be true for
  any continuation in this accepted snapshot.
- Discriminating probe, in memory only (`host/probe-assisted-adjudication-binding.json`; no evidence
  file modified): supplying the wrapper's adjudication fields makes `a8-search-02` pass every
  technical check (financial safety, business-result quality, tool contract, accepted outcome),
  while `a8-link-02` still fails financial safety and business-result quality.
- Inference (labelled): the device and host record shapes are asymmetric in the accepted snapshot;
  either the device should annotate the assisted record like the first record, or the host should
  read `assisted_adjudication`. This is a measurement-contract defect, not a candidate behaviour.
