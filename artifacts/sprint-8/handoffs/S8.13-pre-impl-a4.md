## Rejected hypotheses / alternatives

- **Preserving an existing field on a null argument** (host-side merge) was rejected: the design's
  update semantics are full replacement, and a silent merge would also be a silent decision. The
  reviewer confirmed refusal/manual is the consistent contract.
- **A new error code for the overlap case** was rejected; `STALE_OBSERVATION` with a distinct
  constraint plus a fresh observation is within the approved taxonomy and the reviewer accepted it.
- **Binding an overlapping selection to the existing event** (allowing boundary rewrite) was
  rejected: the design explicitly does not support relocating a stored reading.
- **Mapping classification `Failed` by message alone** was rejected as brittle; the runtime reads the
  journal and compares the service's own reason constants. **Treating every classification failure as
  effect-unknown** was rejected because model unavailability genuinely has no effect.
- **Restoring the two historical inputs from `HEAD`** was rejected after inspection: `HEAD` holds
  `skills/v1` and an earlier tools revision, and the historical preflight requires the v2 bytes.
- **Accepting capture-page value aliases as occurrence evidence** was rejected: both aliases share a
  session and may quote the same text, but a capture-page alias is not bound to the selected span, so
  accepting it would weaken provenance and allow a different occurrence's value. The loaded example
  was corrected instead; the registry and binding checks are unchanged.
- **Adding a `Pending` outcome to the domain enum** was considered and not needed: the journal check
  plus the service reason constants give the same truth without widening a widely consumed sealed
  interface.

## Round-2 finding and round-3 authorization

The reviewer asked which transaction/DAO check stops a competing different-overlapping-span writer
between the runtime pre-check and dispatch, because the repository's exact-identity CAS alone does
not; that assessment closed round 2 as `changes_requested`. Main then explicitly authorized
cycle-1 round 3 for the corrected candidate. The check now lives inside
`EventContextRepository.recordEvent`'s `database.withTransaction` block as
`eventDao.findOverlapping(captureId, spanStart, spanEnd)`, evaluated for the expected-absence insert
before the row is written. Room serialises write transactions on the single database connection, so
whichever writer commits first is visible to the other's read; the second returns `Changed` (runtime
`STALE_OBSERVATION`, effect none) and both cannot commit. The runtime's `findOverlappingEvent`
remains only for the specific repair message. Fresh proof at this snapshot: a direct
repository-level competing-writer test (`NoteEventContextTest`, bypassing the runtime) shows
overlap → `Changed` with one row and a disjoint span → `Stored`; the runtime suite shows the
overlapping reselection refused, two disjoint occurrences stored independently, and an exact-span
correction revised in place. Candidate digests were refreshed after this change.

## Cycle-2 correction (loaded example provenance)

Cycle-1 round 3 closed `changes_requested` because the loaded event-reading example used capture-page
value aliases (`amt_a`/`anchor_a`) with a `select_source` handle (`src_a`). No such path exists:
capture-page aliases bind to `capture:<id>`, `select_source` issues
`source:<cap>:<start>:<end>` aliases, `record_event`/`make_time_anchor` enforce that binding
(`REFERENCE_KIND_MISMATCH`), and a no-event capture issues no anchors. Main authorized cycle 2.
Enforcement and the registry were not changed; the skill content was corrected and its version
bumped to 2. Executable proof (real Room/service): the corrected flow records and verifies one
reading; a capture-only amount alias, a capture-only date alias and a fabricated handle are refused
with effect none and no stored row.
