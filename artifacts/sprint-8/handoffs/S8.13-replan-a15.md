## D1 re-verification: the a14 "inexpressible merchant" conclusion is not supported

The a14 chain reasoned that `valueRefsIn` mints aliases only for AMOUNT/DATE/TIME and that the only
merchant alias comes from an `ask_user` answer, so a stated merchant had no host-issued reference. That
observation about value aliases is true but it does not prove inexpressibility, because the approved
design does not route merchants through a value alias.

1. Approved design `docs/sprint-8-agent-interface-redesign.md` §6.2: `select_source` is to be used
   "once per occurrence, **or to select an exact merchant substring within the same capture**", and
   §6.5 defines `merchant_ref` as a "**Source handle** for an exact merchant substring in this capture".
2. Implementation `AgentToolRuntime.selectSource` (231-341) mints a `SOURCE` handle for any exact,
   token-boundary-safe quote in the current masked source, at exact stored offsets, and returns
   `source_ref`; nothing restricts it to a whole occurrence.
3. Implementation `AgentToolRuntime.recordEvent` (548-552) resolves `merchant_ref` as
   `AgentReferenceKind.SOURCE` and accepts it when `merchantWithin` (1800-1808) holds: same capture and
   merchant span contained in the selected source span. It then rehydrates the merchant display into the
   stored reading (583).
4. The actual frozen `a8-multi-01` overlay source is
   `"Lunch 28,000 VND at Highlands on 2026-10-21 at 12:30; taxi 65,000 VND on 2026-10-21 at 13:05."`
   so `Highlands` is a literal exact substring inside the first occurrence span and can be selected
   separately.

Conclusion (**verified by design text and code reading; runtime execution not yet performed**): the
approved merchant path is expressible through existing tools. The demonstrated gap is guidance, not
host capability:

- `tools/slm/s8_agent_tools_v3.json` `select_source` description says only "Select the exact occurrence a
  reading is about" and mentions returning "the value aliases inside that occurrence"; it never states the
  merchant-substring selection use, while `merchant_ref` demands the resulting SOURCE alias.
- `tools/slm/s8_agent_runtime_skills_v3.json` `event-reading` v2 gives no merchant procedure; its
  `normal` branch says an absent merchant stays null and both examples pass `merchant_ref: null`.
- No example anywhere shows a stated merchant being selected.

So the bounded correct fix is guidance/schema/example alignment, not a new tool or alias kind. The
discriminating runtime proof (source-event plus merchant-substring handle accepted; foreign/out-of-span
handle refused; two-event mapping with no extra event) is designed but has not been executed.
