### 2. Predicate validity against approved boundary

The predicate in `S814IntegratedPhoneInstrumentedTest.kt:1613-1615` is:

```kotlin
val responseContainsSyntheticSensitiveValue = response?.body?.let { body ->
    sensitiveLiterals.any { it.isNotBlank() && it in body }
} == true
```

This predicate is **invalid against the owner-approved privacy boundary**:

- **Contract violation:** Under `docs/sprint-plans/sprint-8.md:66`, `AgentContextManager.kt:48-52`, and `MaskedHostedGateway.kt:165-178`, the owner-approved boundary explicitly guards tool-call arguments (`tool_calls[].function.arguments`) and final user-visible responses (`choices[].message.content`), not private provider reasoning or protocol metadata.
- **Production design alignment:** `MaskedHostedGateway.kt:165-178` enforces that internal provider reasoning never reaches inbound scanning, is scrubbed before outbound continuation, and cannot block a turn, be published, or dispatch an effect.
- **Harness flaw:** By scanning the raw, unparsed HTTP response string with `it in body`, the test harness inspected internal provider reasoning, usage statistics, headers, and identifiers. This conflated internal provider processing with boundary egress, directly violating the approved boundary specification.

### 3. Recoverability of alleged match and corpus susceptibility

- **Recoverability:** The exact alleged match cannot be recovered without guessing.
  The raw HTTP response was not persisted to disk. The detector evaluated only a boolean flag (`any { ... }`) and threw an assertion. In the retained JSON, none of the 30 non-credential fixture literals match any surviving field. Because the removed fields (`reasoning_content`, `usage`, etc.) were stripped without recording the matched literal, category, or character offset, determining what substring triggered the detector is forensically impossible without guessing.

- **Corpus susceptibility to false positives:** High.
  The `sensitiveLiterals` corpus contains unanchored short numeric and timestamp strings:
  - 4-digit numbers: `"9437"` (offline intake amount), `"8337"` (race amount).
  - 5-digit numbers: `"14216"`, `"16137"`, `"38637"`, `"43137"`, `"75637"`.
  - 5-character timestamps: `"09:15"`, `"10:00"`, `"10:30"`, `"22:10"`, `"11:30"`.
  - 10-character dates: `"2098-12-30"`, `"30/12/2098"`.
  An unanchored substring check (`it in body`) across raw JSON payloads is prone to coincidental collisions with token counters, byte offsets, random UUIDs/hashes, epoch timestamps, or provider internal IDs in metadata.

### 4. Evidence-capture / QA failures and minimal safe correction

- **Evidence-capture and QA failures:**
  1. *Premature redaction before diagnostic capture:* The test detected a purported violation on raw bytes, then invoked `privacySafeProviderJson` to scrub the payload before persisting it, discarding the diagnostic evidence needed to substantiate the finding.
  2. *Information loss:* The test stored only `sensitive_response_values_detected = true`, omitting the matched string, category, JSON path, or offset.
  3. *Boundary misalignment:* The test asserted on the entire raw HTTP wire body instead of targeting the approved boundary points.
  4. *Unfalsifiable hard abort:* The test threw `S814FatalPrivacyViolation` immediately, halting the suite and preventing subsequent verification.

- **Minimal safe discriminating correction required:**
  1. *Align detector with approved boundary:* Refactor `S814RecordingTransport.record` to parse the response JSON and evaluate sensitive literal detection strictly against:
     - Assistant public content: `choices[].message.content`
     - Tool call arguments: `choices[].message.tool_calls[].function.arguments`
  2. *Field-aware diagnostic logging:* If a violation is detected at the boundary, record:
     - The JSON path / field where the violation occurred;
     - The category of sensitive literal matched (e.g., `AMOUNT`, `DATE`, `TIME`, `ACCOUNT`);
     - The SHA-256 digest of the offending field value, preserving evidence without logging raw secrets.
  3. *Reasoning isolation check:* Verify separately that outbound continuation scrubbing (`scrubbedOutputItems` / `scrubbedModelContent`) removes reasoning prose before subsequent turns, without asserting on raw inbound reasoning.

- **Incident Classification:** **INDETERMINATE DETECTOR STOP**.
