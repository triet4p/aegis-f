## 2. Particular risk 1 — date-entry crash: predecessor mislabel confirmed, Gold fix verified

- **Predecessor error was real and material.** S6.2-impl-01 diagnosed the interrupted date-range entry as a harness-only `Back`-key problem (handoff §7). Gold proved it was a product crash: `resolveDashboardScope` ordered the two day texts as text, so `Through = 2026-10-3` sorted after `2026-10-16` while naming an earlier day, and `LedgerDateRange.closed` threw `IllegalArgumentException` (`closed` requires `from < through`, `WorkflowQueryTypes.kt:127-136`). Text-ordering plus `closed`'s strict require is exactly a crash path, not a driver artifact.
- **Fix verified in source.** `DashboardScope.kt:129-142` now resolves both ends to instants (`dayStartEpochMillis` / `dayAfterStartEpochMillis`) and refuses (`rangeError`, `range = null`) when `fromStart >= throughExclusive`; `closed()` is only called on a strictly ordered pair. KDoc (`:96-110`) documents the lenient-grammar cause.
- **Contract verified:**
  - Both ends required (empty → per-field refusal, no silent widening).
  - Malformed day (`2026-02-30`) → field refusal, no range (`DashboardScopeTest` malformed case).
  - Reversed zero-padded range (`2026-10-31` → `2026-10-01`) → `"The From date is after the Through date."`, no range.
  - Non-zero-padded pair both directions: `2026-10-16`/`2026-10-3` refused; `2026-9-30`/`2026-10-1` usable as 30 Sept – 1 Oct with exact epoch bounds asserted in the new regression test (`DashboardScopeTest:122-146`).
- **Regression proof is sound, with one stated limit.** Unit: `TEST-…DashboardScopeTest.xml` → `tests="12" failures="0" errors="0"`, including the new test. Phone: the full 69-check run completed in one uninterrupted pass on the fixed build (timestamps 15:25→16:04, per-check `results.json` writes), where the predecessor stopped at the same field entry. The worker is explicit that lenient text was unit-covered both directions but exercised on the phone only through the formerly-crashing entry states, not as a deliberate final scope — accepted as a stated limitation, not a gap, since the crash path is the refused-before-`closed` path the unit test pins.

## 3. Particular risk 2 — pre-existing `TransactionFilter.kt:88` text comparison

- **Still present and correctly characterized.** `resolveDateFilter` (`TransactionFilter.kt:79-113`) compares `fromText > throughText` as text (line 88) and builds an open `LedgerDateRange(...)` directly (lines 97-105), bypassing `closed()`'s ordering require.
- **Cannot crash.** The open data-class constructor (`WorkflowQueryTypes.kt:105-114`) enforces only a non-blank zone, not ordering; an inverted pair yields an empty SQL result (`occurredAt >= from AND occurredAt < through` matches nothing), never an exception. This matches the worker's "does not crash" claim.
- **Cannot be encountered by any S6.2 linked list.** The S6.2 scoped list (`DashboardScopedListScreen`) resolves exclusively through `resolveDashboardScope` (fixed) and never calls `resolveDateFilter`; its only two callers are `DashboardScreen` (`:98`, `:743`). `resolveDateFilter` has exactly one caller: `TransactionListScreen:103` (the Manual saved-transactions list, S6.1/S6.7 territory).
- **Effect if hit via the Manual list:** a lenient reversed pair (e.g. From `2026-10-16`, Through `2026-10-3`) would pass the text check and show an empty list instead of the reversed-range refusal — a minor truthfulness wart in Manual filtering, not a wrong figure and not silent data loss. It does not touch any S6.2 card, total, or drill-down.
- **Disposition:** INFO, non-blocking for S6.2. Endorse routing the cleanup to S6.7 (Manual/filter owner) rather than expanding S6.2 scope. Not an acceptance failure; the "out-of-scope" claim is accepted **only** with this bounded impact statement, not on assertion alone.
