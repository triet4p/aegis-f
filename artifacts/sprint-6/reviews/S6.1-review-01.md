## 4. Acceptance Criteria & Implementation Review

### 4.1 Four Primary Destinations & Labels
- `PrimaryDestination` defines exactly four enum values: `DASHBOARD`, `CHAT`, `REVIEW`, `MANUAL`.
- Labels and semantics:
  - Bottom bar labels: `Dashboard`, `Chat`, `Review`, `Manual`.
  - Spoken content descriptions: `Dashboard`, `Chat / Quick Capture`, `Review notifications` (with `, N waiting` when positive count), `Manual entry`.
  - Semantic properties: `Role.Tab`, explicit `selected` state, combined with visual indicators (bold font weight, primary container tint, 2 dp wide indicator bar or pill badge) ensuring compliance with the rule against color-only status distinctions.
  - Sizing: `heightIn(min = 56.dp)` meets accessible touch target minimums.

### 4.2 Review Count Badge
- `WorkflowQueryService.observeDraftCandidateCount(IntakeReviewStatus.PENDING)` drives the live review count badge in `PrimaryNavigationBar`.
- Displayed as a rounded pill badge `"$count waiting"` directly beneath the Review label.
- Verified on device with synthetic draft showing `1 waiting` badge in screenshot `03-review-inbox.png` and screen reader description `Review notifications, 1 waiting`.

### 4.3 Secondary Routes & Navigation Stacks
- Each destination maintains its own saveable back stack (`dashboardStack`, `reviewStack`, `manualStack`):
  - **Dashboard:** Settings button in `TopAppBar` opens `SettingsRoot` (hub). From there, `Bank notification settings` opens `BankNotificationSettingsScreen`, and `Model setup` opens `LayaProvisioningScreen`.
  - **Review:** Inbox opens `BankDraftReviewScreen(draftId = null, showBack = false)` as root. Selecting a draft opens `BankDraftReviewScreen(draftId = route.draftId, showBack = true)`.
  - **Manual:** Root provides direct access to `Record a transaction` (`ManualRoute.NewTransaction`), `Saved transactions` (`ManualRoute.TransactionList`), and `Manage categories` (`ManualRoute.Categories`). From `TransactionList`, items open `TransactionDetailScreen`, which routes to `TransactionEditorScreen` (Edit mode).
  - **Chat:** Truthful empty state explaining that typed capture is not yet implemented (S6.4), providing direct buttons to `Record a transaction` and `Open Manual`.

### 4.4 State Retention Across Switching, Back, and Recreation
- **Tab Switching:** Hoisting destination state with `rememberSaveableStateHolder().SaveableStateProvider(destination.name)` preserves all child composable state (e.g., input values in open forms). Verified by entering `67890` in the new transaction form, navigating away to Dashboard, and returning to Manual: form contents and amount remained intact (`16-draft-after-tab-switch.png`).
- **Filter Retention:** `transactionFilters` and `transactionFiltersExpanded` are hoisted at the `AegisAppShell` level using `rememberSaveable`. Drilling down from filtered list (`Expense` filter active) into transaction detail and editor, then navigating back, retains the active filter (`1 active filter` in `10-list-after-back.png`).
- **Activity Recreation (`always_finish_activities=1`):** Form with `77777` typed into amount was preserved after home-key and relaunch (`17-recreated-editor.png`).
- **Process Death (`am kill`):** Background process killed while `88888` was typed into form; on relaunch, the activity and form state were accurately restored (`18-process-death-editor.png`).
- **Single Save / No Duplicate Saves:** After process recreation, saving `93,858 VND` added exactly one row to the ledger (`19-saved-after-recreation.png`). Similarly, baseline and post-change test runs `S61B1`, `S61B2`, `S61B3` each produced exactly one recorded entry.

### 4.5 Boundary Evaluation: Editor Back Leaves Without Saving
- **Requirement Analysis:** S6.1 specifies: *"preserve detail routes, unsaved input, back behavior and process recreation... switching/back does not silently discard input or duplicate saves."*
- **Observed Behavior:**
  - In `TransactionEditorScreen.kt`, line 396 and lines 121-124, pressing Back, Cancel, or the system back gesture while in the transaction editor intentionally exits the editor and writes nothing (`onNavigateUp()` drops `NewTransaction` or `Edit` from `manualStack`).
  - The worker explicitly documented this in artifact line 149: *"Back from an unsaved draft still leaves without saving, exactly as before this task; the form explicitly says leaving changes nothing. The S6.1 guarantee exercised here is that switching destinations preserves the draft (and that shell-level back does not reset filters or another destination's state)."*
- **Review Evaluation:** This behavior is correct and matches the architectural contracts of the application:
  1. An explicit Back/Cancel action inside an active transaction editor represents deliberate user abandonment of that transaction form. Discarding form state upon explicit cancellation is standard UX and existing contract.
  2. The S6.1 acceptance criterion ("switching/back does not silently discard input") is fully met: switching between primary destinations does *not* discard open form input, navigating back from a child route (e.g., detail back to list) does *not* discard active filters, and process death restores the open form.
  3. Durable uncommitted draft capture belongs to quick capture notes in S6.4 ("Deliver persistent quick capture... save a source-backed capture independently of notifications"), not the manual transaction editor.
  4. There is no regression or silent shrinkage of acceptance.

### 4.6 Truthfulness & Completeness of Shell vs. Later Tasks
- **Chat Destination:** Correctly and truthfully states that quick capture and conversational assistance are not yet wired up. Does not fabricate AI responses, fake bots, or mock persistent captures.
- **Dashboard Destination:** Conscientiously reuses `CurrentMonthExpenseSummary` for confirmed ledger spending; does not mock or stub S6.2 cards/filters or S6.3 charts.
- **Review Destination:** Truthfully connects to real database query `observeDraftCandidates(PENDING)` and `observeDraftCandidateCount(PENDING)`; does not fabricate S6.6 inline capture splitting or auto-categorization chips.
- **Manual Destination:** Direct access to real transaction commands, catalog, and query services. No fake placeholders.
