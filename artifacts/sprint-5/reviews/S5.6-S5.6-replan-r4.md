## Actionable findings

1. **MEDIUM — A competing request can receive “already running” instead of the required idempotency conflict while the first claim is being registered.** In `app/src/main/java/io/github/triet4p/aegisf/data/WorkflowCommandService.kt:1019-1031`, if a contender finds no durable row but loses `WorkflowClaimGuard.acquire`, it checks the row once and returns `OperationClaim.InProgress` when that row is still absent. `requestClassification` maps this to `Failed(IN_PROGRESS_REASON)` at `:611-615`. The winning request may have a different scope or payload digest; those are only compared with the durable row later in `resolveClaim` (`:1120-1133`). The docs require the same key with a different request or caller to yield `Conflict` (`docs/sprint-5-preparation-commands.md:127-133`), and the documented classification sequence distinguishes an already-running same-key request from durable claim registration (`:241-251`). The worker acknowledges this timing-dependent outcome (`workers/S5.6-replan-a5.md:303-306`); current tests pause at `KEY_TAKEN` but test the same request rather than a conflicting one (`app/src/test/java/io/github/triet4p/aegisf/data/WorkflowCommandServiceTest.kt:1413-1480`). A caller may therefore observe a different outcome for the same key/payload collision depending on whether it arrives just before or after the durable insert. The reservation still prevents duplicate work and writes, but the published idempotency outcome contract is not consistent. **Confidence: high.**
